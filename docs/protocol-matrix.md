# Protocol support

Current inference routes share key authentication, global public model aliases, live workspace grants, key restrictions, routing and per-attempt accounting. Support means the bounded protocol subsets below (including native Anthropic Messages images/thinking), **not universal SDK/vendor option compatibility**. Model `supported_protocols` and request-specific profile checks may narrow each row further.

| `anthropic` | Representable subset via Messages | No | Native Messages; native token counting | No | No | No |

**Guardrails (input only, #840).** Every generation request (Chat Completions, Responses, Messages, `/v1/messages/count_tokens` and gateway-run batch lines) and every embeddings request runs its workspace's guardrail rules on its input before routing and admission; a native batch, whose lines this release does not read, is refused at create time by an enforcing rule (`guardrail_not_supported`; use `metadata.omg_mode=gateway`) ([guardrails design](guardrails-design.md)): a refused request reserves nothing and reaches no provider. The refusal keeps each protocol's error shape and adds an `error.guardrail` object (`policy_id`, `rule_id`, `stage`, `category`, `detector`; never matched text) with `x-should-retry: false`: `guardrail_input_blocked` (400) for a finding of a blocking rule, `guardrail_not_supported` (400) when an enforcing rule cannot read part of the request (an image, audio or an encoded document; phase 1 rules cannot name rerank, System One, speech, images, transcription, realtime or video, which are not checked), `guardrail_detector_failed` (503) for a fail-closed rule this release cannot run. When the inspection cannot finish now (no scan slot in time, the custom-pattern budget spent, a policy this release cannot read), the answer is the retryable `guardrail_unavailable` (503, `Retry-After: 1`, no `x-should-retry: false`) whatever the rule's `on_error`; a key with 600 requests in a minute on one replica that wrote decision rows and were never admitted (refusals included) gets `guardrail_rate_limited` (429, `Retry-After`) before any scan; gateway-run batch lines are exempt and retry `guardrail_unavailable` themselves ([guardrails design §4](guardrails-design.md#4-detector-interface)). OpenAI shape: `code` as above, type `invalid_request_error` (`server_error` for the 503s, `rate_limit_error` for the 429). Anthropic shape (no machine code): type `invalid_request_error`, `api_error` for `guardrail_detector_failed`, `overloaded_error` for `guardrail_unavailable` and `rate_limit_error` for the 429, and `error.guardrail` tells a guardrail refusal apart (it is absent when no rule is named: a policy that could not be read, or the 429). Response text is not inspected.

This table is one source of truth in the gateway (`providers::capabilities`): every adapter's `supports_protocol`, the pre-admission `unsupported_capability` check, route validation (`400 route_unsupported_capability` when a route's connection serves none of its model's protocols, see [management API](management-api.md#infrastructure-and-catalogs)), readiness and the Add model form all read it.

A model's protocols belong to one workload: Chat/Responses/Messages combine, while embeddings and each other kind stand alone. Images, audio, realtime, video, batch, Rerank and System One routes return **400 `unsupported_capability`** when the model exists but has no deployment that declares the protocol on an adapter supporting it. Chat/Responses/Embeddings keep 501 for unsupported capabilities. Messages uses Anthropic-shaped 400 refusals.

Permanent `unsupported_capability` refusals carry `x-should-retry: false`, honored by the official OpenAI and Anthropic SDKs even on HTTP 501. Statuses and protocol-specific error bodies are unchanged. Transient rate/concurrency failures, upstream 502/504 errors and cooling-down 503s are not opted out of SDK retries; cooling-down responses retain `Retry-After`. An SDK retry is a new gateway HTTP request with its own admission and durable reservation if dispatched; unknown usage retains its hold. This is separate from the gateway's [explicit failover policy](routing.md): the gateway does not implicitly retry an upstream request or fail over after returning a stream.

Unsupported combinations fail explicitly. Local labels do not mean every installed server/model supports all fields. Ollama native embedding follow-up has source and mocked tests, but this documentation refresh does not claim a fresh pass or live-server certification; consult [local profile notes](../apps/gateway/src/providers/local/README.md). [Bedrock](bedrock.md) documents its separate transport.

## Client labels (Logs sessions and apps)

Every inference route accepts two optional, untrusted labels used only to group and display requests in Logs ([management API](management-api.md#logs)):

- **Session id**: the `X-Session-Id` header; otherwise, in the body, OpenAI `metadata.session_id` then `user` (Chat Completions, Responses) or Anthropic `metadata.user_id` (Messages). Embeddings and the other workloads take the header only.
- **App name**: the `X-Title` header.

A label is recorded only when it is 1–128 (session) or 1–200 (app) characters, valid UTF-8, without control characters or leading/trailing whitespace, and sent once; anything else is silently not recorded and never fails the request. Labels are metadata, not authorization or attribution: they are stored on each attempt of the root request, shown to whoever may see that request, cleared by execution-detail retention, and are not authorization input. They are never forwarded upstream, including Messages `metadata.user_id`. Other protocols' `user` and `metadata` are not sent to providers (they do not change generation); OpenAI `metadata` keeps its documented bounds (at most 16 pairs, keys 1–64 and values up to 512 characters, else 400) and is not stored beyond `session_id`. Anthropic `metadata` accepts only `user_id` (at most 256 characters). Treat a session id that may identify an end user (such as `user`) as visible to workspace administrators and, for Team/Project workspaces, to Platform Admins and Auditors.

## Chat Completions

One choice (`n` absent or 1); messages with system/developer/user/assistant/tool roles whose content is a string or an array of `text` parts (joined into one text, as Responses input parts are), and, on user messages, [inline images](#image-input); function tools and tool-call/results; `temperature`, `max_completion_tokens` (or its legacy alias `max_tokens`), streaming and optional `stream_options.include_usage`; `user` and `metadata` as [client labels](#client-labels-logs-sessions-and-apps) only. Audio and file parts, structured output, reasoning, log probabilities and arbitrary extensions are rejected.

**Nullable defaults.** Omitted or null `stream` means non-streaming; explicit `false`/`true` is unchanged. Existing nullable supported options (`temperature`, maxima, `n`, `stream_options`, `metadata`) also treat null as omission. This is field-specific: `tools`, message `tool_calls` and `stream_options.include_usage` are not nullable in OpenAI SDK 7.28 and remain strict. Assistant message `refusal:null` is public no-refusal metadata and is accepted without being forwarded; non-null refusal content remains unsupported, and null does not make an otherwise empty message valid. Other roles cannot send `refusal`, even null. Unknown fields such as `parsed:null` and unsupported options remain rejected even when null.

**No-argument functions.** Omitting a Chat function's `parameters` defines an empty parameter list (OpenAI SDK contract). The gateway canonicalizes only omission to `{"type":"object","properties":{},"additionalProperties":false}`: only the empty object satisfies this schema, unlike the unconstrained schema `{}`. Explicit object schemas pass through unchanged; explicit null/nonobject parameters and unknown function fields remain invalid. Omitted `strict` stays absent, not `true`; explicit strict values retain each adapter's existing capability rules. This is schema normalization, not a new runtime argument validator or strict-generation guarantee.

**Output maximum.** `max_tokens` (still sent by many OpenAI-compatible clients and older SDK code) is accepted as an alias of `max_completion_tokens`. Sending both is accepted only when they are equal; different values (or 0) are 400 `invalid_request_error`. The one value is the admission reservation's output bound and the upstream maximum: OpenAI and OpenRouter receive `max_completion_tokens`; local profiles (`openai_compatible`, `vllm`, `sglang`, `ollama`) receive `max_tokens`; Anthropic receives Messages `max_tokens` and Bedrock Converse `maxTokens`. Batch lines follow the same rule. Responses keeps `max_output_tokens` and rejects both Chat names.

Local transports translate the accepted maximum to upstream `max_tokens`. All local profiles reject strict function guarantees. Ollama rejects explicit tool choice; generic compatible rejects required/named choice. Anthropic Chat accepts leading system/developer text but rejects strict schemas, temperature above 1 and non-object tool arguments. Chat Completions and Responses maxima are optional, including for priced generation. When omitted, admission pins the selected price's positive output ceiling as both the reservation bound and the maximum sent upstream. Each failover attempt resolves its own price and cap. Invalid explicit maxima return 400 without dispatch; an unusable server default returns 503. Native Messages still requires `max_tokens`.

```json
{"model":"company/smart","messages":[{"role":"user","content":"Hello"}],"max_completion_tokens":32,"stream":false}
```

## Responses

Stateless native OpenAI text/function subset: `model`, string or nonempty item-list `input`, `instructions`, `max_output_tokens`, `temperature`, `stream`, `store:false`, flat function `tools`, supported `tool_choice`, and `text:{"format":{"type":"text"}}`; `user` and `metadata` as [client labels](#client-labels-logs-sessions-and-apps) only.

Message items support user/assistant/system/developer and text/input-text (assistant output-text also accepted), and, on user messages, [`input_image`](#image-input). Function calls use `call_id,name,arguments` (string); results use `call_id,output` (string). Supported message/function-call items accept optional string `id` and `status` (`in_progress`, `completed`, `incomplete`); function-call outputs also accept explicit null for these two metadata fields. IDs/statuses are validated read-only metadata, never server-side lookups or authorization. Tool correlation uses `call_id`, not the item `id`. Assistant output-text accepts omitted or empty `annotations`; nonempty annotations/citations are explicitly rejected. This lets clients reuse JSON `output` or a terminal stream event's `response.output` in stateless followups without adding a maximum or `store:false`. SDK-only parsing extensions (such as `parsed`/`parsed_arguments`) are not wire fields and remain unsupported. Tools are flat Responses definitions, not nested Chat envelopes. OpenAI strict function schemas can be forwarded where supported.

Omitted or null `stream` means non-streaming. Omitted, null or false `store` means stateless operation under the gateway's privacy subset, not OpenAI's provider-side storage default; `store:true` is refused before admission. Existing nullable supported options (`instructions`, `max_output_tokens`, `temperature`, `metadata`) treat null as omission. `tools` is optional but not nullable in OpenAI SDK 7.28; `tools:null`, malformed values and unknown/unsupported fields with null remain rejected. This does not enable hosted tools, reasoning, structured output or stateful followups.

Upstream requests explicitly set `store:false`. Upstream assistant message items may carry `phase: "commentary"` (preamble) or `phase: "final_answer"`. Text from both phases is returned as output text in upstream order. Any other phase value fails as an invalid upstream response rather than being dropped. `store:true`, `previous_response_id`, background/stateful operations, hosted tools, structured output, reasoning items, image files and URLs, audio and nonempty annotations are unsupported. Max-token/content-filter terminal results are incomplete, not completed. This is not a universal chat-to-agent/state mapping.

## Image input

Chat Completions `image_url` parts, Responses `input_image` items and Messages `image` blocks with a base64 source carry inline images (#24): on user turns, and on Messages also in a `tool_result`'s content. A Messages image block goes through the same validator as the others and becomes the same canonical image, so every route below takes it in its own wire; an assistant turn's image, which native Anthropic has always accepted, still goes only there (translated routes refuse it naming `messages.content.image`). Messages batch lines (4 MiB each, outside the image input buffer) take images as Messages requests do; Chat and Responses batch lines refuse them. On a native Anthropic route a Messages request is forwarded as its own validated envelope, and its images need no `image_input` opt-in, as before; a translated route needs the opt-in, as for Chat. A `tool_result`'s image reaches Anthropic and Bedrock (Converse takes images in a tool result) and is refused with 400 naming `tool_result.content.image` on OpenAI-style and local routes, whose tool messages are text only.

- **Accepted form:** a base64 data URL, `data:image/png;base64,…` (also `image/jpeg`, `image/webp`, `image/gif`), exactly that prefix and strict padded base64. The decoded bytes must start with the declared type's signature (PNG, JPEG, `RIFF…WEBP`, `GIF87a`/`GIF89a`); a mismatch is 400. OpenAI's optional `detail` (`auto`, `low`, `high`) is carried to the wires that take it (OpenAI, OpenRouter, the local profiles); Anthropic and Bedrock have no such hint, so there `auto` (the provider's own behaviour) is accepted and `low` or `high` is refused with 400 naming `detail`, never dropped.
- **Refused before routing, with the field named (400):** an `http(s)` URL or any other URL (the gateway never fetches a caller's URL and never asks a provider to), a Responses `file_id` or `input_file`, a Chat `file` or `input_audio` part, an image outside a user message, more than 20 images in one request, and an image over 5 MiB decoded (checked on its base64 length before it is decoded). Chat Completions and Responses batch lines (`/v1/batches`) refuse images; Messages batch lines take them as Messages requests do.
- **Routes:** a route takes images only when its connection's adapter carries them and its deployment allows them. The adapters that carry them: `openai` (Chat Completions and Responses wires), `openrouter`, the local OpenAI-compatible profiles (`openai_compatible`, `vllm`, `sglang`, `ollama`), `anthropic` (a Messages `image` block with a base64 source) and `bedrock` (a Converse `image` block of the decoded bytes), each as the provider's own image part. Only `openai` serves Responses at all, so Responses images reach only `openai` routes; on the others Responses is 501 `unsupported_capability`, with or without images. The deployment opt-in is `image_input` ([management API](management-api.md), off by default): enable it only for an upstream model that accepts images and bills them as input tokens. Routes without both are skipped before the route plan, so failover never lands an image on them; when none is left the request is refused with 501 `unsupported_capability` before admission, with nothing held. An adapter refuses an image request in its encoder too, before any request is built, when its wire cannot carry it.
- **Provider limits:** an image a route's provider would refuse is refused before admission with 400 naming `image`, so no hold is taken for a request the provider cannot accept. The gateway's own bounds above apply first; the provider's, as each documents them, are:

  | Wire | Per image | Images per request | Pixels per side | Request |
  | --- | --- | --- | --- | --- |
  | Anthropic | 10 MB of base64 | 100 | 8000 | 128 MB |
  | Bedrock Converse | 3.75 MB decoded | 20 | 8000 | 20 MB |

  The Bedrock row is what Bedrock documents for Claude models on Converse. Another model family on Bedrock may take less; a request within this row that such a model refuses is refused by Bedrock after admission.

  The request size counts the images' base64 and everything else the request sends (text, tools, tool arguments, schemas). Megabytes are taken as 10^6 bytes, the smaller reading. The pixel limit is checked when the image's header states its dimensions (PNG, JPEG and WebP headers; a GIF's screen widened by each frame's extent); a header the gateway cannot read leaves the dimensions to the provider. A blank text part beside an image carries nothing and is not sent on these two wires, which refuse a blank text block.
- **Admission and settlement:** unchanged. The hold covers the price's `input_token_limit` at its input rate, the worst case that price allows; settlement uses the provider's observed usage. There is no image meter: a model that also charges per image cannot be priced, so its deployment must keep `image_input` off. A route without a complete input price is refused for a budgeted key exactly as for text.
- **Body size:** a body of these routes (Chat Completions, Responses, Messages and its token count) may exceed the shared 2 MiB limit only when it declares its `Content-Length`, is at most `GATEWAY_MAX_BODY_BYTES_IMAGE_INPUT` (default 20 MiB), fits this replica's image input buffer ([operations](operations.md#image-input-memory)), arrives without a pause of more than 10 s, at 128 KiB/s or more on average from its start (after a 128 KiB allowance), and within 180 s, and everything in it but its images' data URLs fits in 2 MiB. Otherwise: 413 `payload_too_large` (over a cap, a streamed body past 2 MiB, or more than 2 MiB outside image data), 408 `request_timeout` (a stalled body), or 503 `image_input_busy` with `Retry-After: 1` while the buffer is full. Authentication and the length checks run before any body byte is read, and the 2 MiB outside image data is measured on the received bytes before anything parses them (at most the 20 longest string values that are image data are set aside: a whole image URL, or a `data` key's value of padded base64, as a Messages source has), so a large body never parses into more structure than a text body can. After the parse, the bytes outside the request's validated images must still fit in 2 MiB: a long base64 string under any other `data` key, in a text block or in a tool input is refused with 413.
- **Privacy:** image bytes are never logged, stored or put in an error body, a metric or a trace; the canonical type that holds them has no `Debug`, `Display` or `Serialize` (a compile-time assertion).

```json
{"model":"company/vision","messages":[{"role":"user","content":[{"type":"text","text":"What is in this picture?"},{"type":"image_url","image_url":{"url":"data:image/png;base64,iVBORw0KGgo…","detail":"low"}}]}]}
```

## Messages

Requires exactly one `anthropic-version` header: `2023-06-01` or `2026-10-21` (the version current Anthropic SDKs send, #430). Under `2026-10-21` the gateway applies that version's request rules: `temperature`, `top_p` and `top_k` are refused with **400** (a well-typed value or `null` names the field and the version; an ill-typed value gets the generic 400), even at their default value. The version's other two rules are already met under both versions: `document` blocks and `citations` are not part of the supported grammar and are refused. A `system`-role message (a stable Messages API feature that the current SDKs' message types include) is refused with **400 `messages.role`** under both versions; use top-level `system`. Native Anthropic routes therefore send `2023-06-01` upstream for either client version, because the forwarded request means the same under both. `/v1/batches` lines with the `/v1/messages` endpoint carry no version header and follow the `2023-06-01` rules. `/v1/messages?beta=true` uses the same exact method/path policy as `/v1/messages`; queries do not create another authorization route. All generation adapters can serve Messages when the model declares `messages`. See [Claude Code setup](claude-code.md).

#### Structured output and strict tools on Anthropic and Bedrock routes

- **Anthropic.** `output_config.format` and tool `strict` are forwarded in the validated request unchanged in content: the gateway re-serializes the validated JSON, so object keys reach Anthropic in sorted order (key order is not preserved) and numbers in their canonical form. Anthropic's structured-outputs documentation (checked 2026-11-23) lists both as generally available on the Messages API with no beta header: `output_config.format` replaced the beta-only `output_format` parameter, which still needs `structured-outputs-2025-11-13` and is not part of the gateway grammar (400 naming the field). The gateway adds no beta header; client beta values are forwarded under the usual denylist. Anthropic validates the schema (its supported subset, `additionalProperties:false`, complexity limits) and returns 400 for one it rejects. A Chat Completions strict tool on a native Anthropic route is still refused, because the translated tool encoding has no `strict` field.
- **Bedrock Converse.** `output_config.format` becomes `outputConfig.textFormat` (`type:"json_schema"`, `structure.jsonSchema.schema` is the schema serialized as a JSON string, unchanged in content but with object keys sorted (key order is not preserved); no name or description). A `strict:true` tool becomes `toolSpec.strict:true`, for Chat Completions and Messages clients alike (Bedrock serves no Responses); `strict:false` is Converse's default and is not sent. Support differs by model, and Bedrock decides it per request: a model or inference profile that cannot honour the field returns a validation error, which the gateway surfaces as HTTP 400 `invalid_request_error` without retrying. The gateway keeps no per-model list for these fields (as for `toolResult.status`), so a model family released later is never refused by a stale list. Effort and thinking controls are unchanged: effort is dropped and thinking is refused, because Converse has no model-independent thinking control (Claude models take `thinking` only through model-specific `additionalModelRequestFields`, and tool loops would need signed reasoning history that translated routes do not return).
- **Neither route validates model output against the schema.**

#### Reasoning and structured output on OpenAI-style routes

Delivery 3 maps these fields in the OpenAI and OpenRouter adapters, for Messages requests only. Chat Completions and Responses requests keep their own rules: they still refuse reasoning and structured output and never receive reasoning text. Their strict tools were already sent as `function.strict`; on OpenRouter, which serves Chat Completions but not Responses, a Chat Completions strict tool now also sets `provider.require_parameters:true` (see below).

- **OpenAI Chat.** `output_config.effort` is sent as `reasoning_effort` with the same value, since OpenAI's enum has the same five values. `thinking` is dropped: Chat has no thinking budget, and no on/off value is accepted by every reasoning model. So with `thinking.type:"disabled"` an explicit effort is still sent (unlike OpenRouter, which can turn reasoning off). Some models reject some efforts, and non-reasoning models reject `reasoning_effort`. That upstream refusal returns 400 `invalid_request_error`; the gateway does not retry without the field. OpenAI native batch lines for `/v1/messages` use the same encoding.
- **OpenRouter.** OpenRouter's `reasoning` object takes an effort or a token budget, never both:
  - An explicit `output_config.effort` becomes `reasoning.effort`. A thinking budget sent alongside it is dropped.
  - Otherwise `thinking.type:"enabled"` becomes `reasoning.max_tokens` (the budget), and `adaptive` becomes `reasoning.enabled:true`.
  - `thinking.type:"disabled"` becomes `reasoning.enabled:false` and drops any effort.
  - `thinking.display:"omitted"` adds `reasoning.exclude:true`.

  OpenRouter ignores `reasoning` for models without reasoning support.
- **Structured output and strict tools.** `output_config.format` becomes `response_format: {"type":"json_schema","json_schema":{"name":"output","schema":…,"strict":true}}`. The name is fixed because Messages has none and OpenAI requires one; `strict` is true because Messages structured output is schema-constrained. Tool `strict` is sent as `function.strict` with the same value. On OpenRouter, structured output or any `strict:true` tool also sets `provider.require_parameters:true`, so the request is routed only to providers that support every sent parameter instead of having them silently ignored. This applies to a `strict:true` tool from every client protocol OpenRouter serves (Chat Completions and Messages; it serves no Responses). When no provider for the model supports every sent parameter, OpenRouter refuses the request (OpenRouter does not document the status). Any OpenRouter 4xx other than 401, 402, 408 and 429 reaches the client as HTTP 400 (`upstream_rejected` on Chat and Responses, `invalid_request_error` on Messages), and the gateway does not retry without the flag. How strictly a schema is enforced still depends on the serving provider. The gateway does not validate model output against the schema. The schema of `output_config.format` and of a `strict:true` tool must satisfy the provider's strict-mode rules; for OpenAI that means `additionalProperties:false` on every object, every property listed in `required`, and only OpenAI's supported keyword subset. A schema that Anthropic accepts can therefore be refused upstream. The client then gets the gateway's generic upstream refusal, 400 `invalid_request_error` "The provider rejected the request", without the provider's reason.
- **Refusals.** Under strict structured output, an OpenAI or OpenRouter model can decline with a `refusal` string and null content. For Messages requests, that reply ends with `stop_reason: "refusal"` and no content, in JSON and SSE. The same applies to OpenAI native batch lines for `/v1/messages`. The refusal text is the provider's explanation, not output: it is not returned, is never logged, and counts toward the 16 MiB Messages output bound. Reported usage settles as usual. A refusal together with content or tool calls, or a `refusal` that is not a string, is an invalid upstream response (502). Chat Completions and Responses clients still get 502 for any non-empty `refusal`, because their codecs have no way to return it.
- **Reasoning text.** OpenRouter's `reasoning` string, and local servers' `reasoning_content` or `reasoning` string (a server that sends both must send the same text), reach Messages clients as `thinking` blocks without a `signature`. A signature is never invented. As on a native route, the text is returned only when the request asks for thinking (`enabled` or `adaptive`) without `display:"omitted"`; otherwise it is withheld (its tokens still count as output). JSON replies put the thinking block before the text and tools. Streams open a new block whenever the output switches between reasoning and text, in arrival order, and close each block before the next opens; tools follow at the next indexes. OpenRouter's `reasoning_details` repeats the text in provider-specific envelopes and is not returned. OpenAI Chat returns no reasoning text. Reasoning text counts toward the 16 MiB Messages output bound and the first-token time. It is never logged. Its tokens are already part of the reported output count, so holds and settlement are unchanged.
- **Replay.** Clients such as Claude Code send these unsigned blocks back in the assistant history. Translated routes remove them like other thinking history. An assistant turn that held only `thinking` is removed entirely, so the upstream can receive two consecutive user turns, which the OpenAI Chat wire accepts. A native Anthropic route cannot forward a thinking block without its signature, so it returns 400 `thinking` before admission. A `signature` that is empty or only whitespace counts as no signature; SDKs replay translated blocks with `"signature": ""` after a switch back to a Claude model.

**Beta headers are an open list**, following Anthropic's [gateway protocol](https://code.claude.com/docs/en/llm-gateway-protocol) and [beta-header grammar](https://platform.claude.com/docs/en/api/beta-headers). New Claude Code beta versions must not break simply because the gateway has not seen their names. `claude-code-20250219`, `extended-cache-ttl-2025-04-11`, tool-search, effort, OAuth and structured-output betas pass through unchanged. Accepting a beta does not enable unsupported body fields or server tools; those remain independently validated. Cache TTLs still require the priced categories below, including when paired with extended-cache-ttl.

A small reviewed denylist (`providers::messages::DENIED_BETA_PREFIXES`) refuses tokens starting with (case-insensitive):

- `context-1m-`: long-context premium pricing is not modeled.
- `code-execution-`, `web-search-`, `web-fetch-`, `computer-use-`: hosted capabilities/extra charges are not supported.
- `files-api-`, `mcp-client-`: upstream file and remote-server capabilities are not supported.

Every comma-separated token across repeated headers is checked, including on translated Messages routes. Bounds remain 16 header values, 1–1024 header-safe ASCII bytes each (space/tab allowed), 32 nonempty tokens total. Whitespace is ignored only for prefix checks; original accepted values are forwarded verbatim, not reconstructed. Denied tokens return HTTP 400 with Anthropic's exact recovery shape before admission:

```json
{"type":"error","error":{"type":"invalid_request_error","message":"Unexpected value(s) `context-1m-2025-08-07` for the `anthropic-beta` header. Please consult our documentation at docs.anthropic.com or try again without the header."}}
```

Multiple denied names are joined with `, ` in request order; allowed names are not listed. Claude Code recognizes the `Unexpected value(s)` prefix and can automatically retry without rejected betas. Operators can also set `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS=1` on clients to disable experimental capabilities. Malformed/oversized headers receive a generic named `anthropic-beta` 400. Denylist changes require a GitHub issue with vendor capability/pricing evidence and a wire/refusal contract; there is no client-controlled override.

**Cache-aware admission.** Native requests with cache hints require a pinned v2/v3 price with explicitly priced cache reads (`read` / `cache_read_tokens`), since repeated prompts may hit the cache, plus an explicitly priced `write_5m` / `cache_write_5m_tokens` category for absent/5-minute TTL and `write_1h` / `cache_write_1h_tokens` for 1-hour TTL. Mixed TTLs require both, and the existing conservative monetary bound must be finite. Missing prices, v1 aggregate-only pricing and unknown/not-applicable required categories return 400 naming `cache_control`, before any reservation or upstream call, even without a workspace budget. Publish a new immutable compatible price; existing prices/history are not rewritten. Anthropic's usual 5-minute/1-hour write rates are 1.25×/2× base input respectively; operators must publish the applicable model's rates. Existing conservative v2/v3 bounds reserve the full pinned input ceiling independently in each priced input/cache category plus the output maximum, covering at least all input written at the highest requested rate, including rounding. Settlement still charges only observed disjoint categories, never the aggregate write count plus its TTL allocations. Cache-enabled batch lines use gateway-run per-line admission, not native Message Batches, until native batch plans carry TTL requirements.

`thinking.budget_tokens` must be at least 1024 and below `max_tokens`; the budget is included in, never added to, the unchanged output reservation. Context edits support `clear_tool_uses_20250919` and `clear_thinking_20251015`; new edit types require an explicit rule. JSON schemas and tool inputs are application data, not gateway field allowlists. Image URL sources are refused before dispatch: neither the gateway nor the upstream may fetch a caller URL. Base64 sources accept PNG, JPEG, GIF and WebP with strict padded base64, matching format magic, at most 5 MiB decoded per image and 20 images per request (the overall 2 MiB HTTP body cap still applies). No inference credential, prompt body or thinking signature is logged or stored by this path.

Native `stream` and `tools` remain nonnullable. Omitted `tool_result.content` is canonicalized to `""`; its error status is preserved independently. The required `tool_use_id` preserves correlation. Explicit null content and null/nonboolean error flags remain invalid. `is_error:true` stays a failure on every route. Native Anthropic preserves explicit true/false and omission verbatim. OpenAI and OpenRouter Chat and all local profiles (`openai_compatible`, `vllm`, `sglang`, `ollama`) prefix only failed tool-message content with the exact string `[tool_error]` followed by one newline, then the original canonical text (including empty text). A successful result can begin with the same marker. Chat recipients cannot infer a trusted status bit from the text. Bedrock Converse keeps the text unchanged and sets only failed results to `toolResult.status:"error"`. False/absent flags leave translated text and wire fields unchanged; the flag belongs to each correlated result, never the entire turn. Existing block bounds and adapter correlation checks still apply. Native Anthropic keeps block and turn order, including mixed tool results/images/text; string message content becomes a single text block. Translated routes consolidate text within each wire message, not across turns; parallel assistant tool calls remain together in one canonical assistant turn. Correlated results remain immediately after that turn (one canonical result per call; Converse groups them into one user message).

Bedrock evaluates support for the explicit error status on the selected model or inference profile. AWS documents support for Amazon Nova and Anthropic Claude 3 and 4 models. A Bedrock validation refusal for that field returns HTTP 400 if it arrives before a response stream opens. After the stream opens, a validation exception ends the HTTP 200 Messages stream with an `error` event of type `invalid_request_error` and no `message_stop`. Loopback SDK tests exercise both Converse and ConverseStream, check the correlated wire blocks, and count attempts. [AWS ToolResultBlock](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_ToolResultBlock.html).

Messages uses Anthropic-shaped errors, including authentication and outer body-limit errors. Provider context overflow becomes **400 `invalid_request_error`, `prompt is too long`**; overload becomes **529 `overloaded_error`**; rate limits remain **429 `rate_limit_error`**. Ordinary error messages are at most 1 KiB, contain no upstream diagnostic bodies/secrets, and never echo serde value diagnostics. The beta-refusal compatibility message is the narrow exception: it reflects only the already-bounded client beta names (at most 17 KiB of message text), preserving exact names for recovery; names are not embedded in inference telemetry or logs. Upstream error classification reads at most 16 KiB and retains no diagnostic text. Explicit structured codes take precedence over diagnostic prose; the only HTTP/SSE text fallback is native Anthropic `invalid_request_error` with the documented `prompt is too long:` prefix (or exact phrase). Bedrock's SDK fallback is likewise restricted to native `ValidationException` input-length prefixes. OpenRouter keeps its account-credit (402), moderation (403) and timeout (524) status meanings.

Streams send `message_start` when the upstream stream opens, before usage is observed. Its `usage` is `{"input_tokens":0}`, a strict-client placeholder; `message_delta` reports observed input/cache/cumulative output counters. Missing usage stays unknown for accounting and keeps holds; other unknown counters are omitted, not zero. Errors before completion emit an `error` event without successful termination; the response was already a `200`. How an error inside a stream is classified is [below](#errors-inside-a-stream). Messages output is bounded to **16 MiB**; Responses remains at 4 MiB.

### Errors inside a stream

A failure after the `200` ends the stream with one terminal error event and no finish marker (`[DONE]`, `message_stop`, `response.completed`). Its class is the one the same error has as an HTTP response (provider error events: [rules and tables](provider-adapters.md#failures-inside-a-returned-stream); Bedrock exception frames: [table](bedrock.md#exception-frames)), or `upstream_unavailable` for a transport failure (a reset, a truncated stream, or corrupt Bedrock binary framing), or `invalid_upstream_response` for a frame that arrived whole but is malformed (#614, #622). The terminal error each client sees is the same as the class produces anywhere else:

| Class | Chat completions: `error.code` and `error.type` | Responses: `error` event `code` | Messages: `error.type` | Counts against routing health |
| --- | --- | --- | --- | --- |
| `Busy` | `rate_limit_error` | `rate_limit_error` | `rate_limit_error` | yes |
| `Overloaded` | `overloaded_error` | `overloaded_error` | `overloaded_error` | yes |
| `UpstreamUnavailable` | `upstream_unavailable` | `upstream_unavailable` | `overloaded_error` | yes |
| `Timeout` | `timeout_error` | `timeout_error` | `api_error` | yes |
| `UpstreamRejected` | `upstream_rejected` | `upstream_rejected` | `invalid_request_error` | no |
| `ContextLength` (Messages clients only, from a provider's context error) | `context_length_exceeded` | `context_length_exceeded` | `invalid_request_error` | no |
| `Configuration` | `provider_configuration_error` | `provider_configuration_error` | `api_error` | no |
| `InvalidUpstream` | `invalid_upstream_response` | `invalid_upstream_response` | `api_error` | no |

So an Anthropic `rate_limit_error` inside a stream reaches a chat client as `rate_limit_error` (it used to be `invalid_upstream_response`), an Anthropic `api_error` reaches a Messages client as `overloaded_error` (it used to be `api_error`), and a reset reaches every client as `upstream_unavailable` (already true for SSE; newly classified this way for Bedrock). SSE EOF before a terminal frame now counts against health, including local servers missing `[DONE]`; complete invalid UTF-8 SSE lines remain invalid responses. Nothing else about the stream changes: it is still a `200`, still returned before the first event is polled, never failed over or retried, and the attempt settles with unknown usage and its hold retained.

### Errors inside a non-stream 200

A provider error object returned inside an HTTP 200 to a **non-streaming** request (chat completions, Messages, Responses, embeddings, images, audio, rerank and System One) is classified like the same error inside a stream, by the same name table ([rules](provider-adapters.md#a-provider-error-inside-a-non-stream-200)), unless the body also carries output or nonzero usage: then it is `InvalidUpstream` (#665). Each client gets the class's ordinary HTTP error, as in the table above, with that class's HTTP status (for example 429 for `Busy`). Client-visible changes: a 200 rate-limit or quota error from OpenAI chat, a local profile, Responses or Anthropic used to reach chat and Responses clients as `invalid_upstream_response` and now reaches them as `rate_limit_error`; a 200 rate limit with a string code from OpenRouter used to be `upstream_unavailable` and is now `rate_limit_error`; an unrecognised 200 error on OpenAI, local, Responses and Anthropic is `upstream_unavailable` instead of `invalid_upstream_response`; a 200 error next to output or usage, which OpenRouter and Messages clients used to classify by its name, is now always `invalid_upstream_response`. No upstream text reaches the client.

Native Anthropic `refusal` and `model_context_window_exceeded` stop reasons are preserved exactly in JSON and SSE, including empty refusal output. They are distinct canonical outcomes, not `max_tokens` or generic filtering. Chat Completions maps them to `content_filter` and `length` respectively. The text-only Responses codec (including Anthropic native batch Responses lines) maps them to `incomplete` with `content_filter` and `max_output_tokens` respectively; this does not enable interactive Anthropic Responses. Responses text stays `output_text`, including deltas already emitted: typed refusal parts and retrospective relabeling are not supported. Existing Logs telemetry uses its coarser `content_filter`/`length` labels. Missing usage remains unknown and retains accounting holds; a valid stop reason alone never proves zero usage. Unknown/malformed stop reasons, missing terminal events and malformed tool events still fail rather than fabricating success.

Native Anthropic JSON preserves validated content blocks in order. Native streams preserve validated text/tool/thinking/redacted-thinking block lifecycles and thinking/signature deltas without reconstructing signatures or duplicating text. Usage and successful termination still require the existing upstream terminal and engine settlement path. Typed refusal blocks, hosted tools/`pause_turn`, audio and other metadata fields remain outside these deliveries; reasoning and structured output on OpenAI-style routes follow [their rules](#reasoning-and-structured-output-on-openai-style-routes). The table above specifies when cache/thinking/image/structured-output fields are forwarded, dropped deliberately or refused. `/v1/messages` accepts one Bearer or `x-api-key`, never both; other inference routes use Bearer only. Repeated/conflicting credential headers fail.

### Token counting (`POST /v1/messages/count_tokens`)

Anthropic's counting endpoint, handled by the gateway (#72), never passed through. It is also reached as `/v1/messages/count_tokens?beta=true`, under the same exact method/path policy.

- **Authority.** Inference keys only (Bearer or `x-api-key`, one of them); inference keys never authorize management, and admin or management credentials never authorize this route. The workspace and key come from the validated key, never from the request. The model is resolved live like an inference request, never from the per-replica cache: an unknown model, one not granted to the key's workspace, or one excluded by the key's restriction is 404 `not_found_error`. A model the key may use but with no enabled deployment serving the `messages` protocol is 501, as for generation. A key revoked, expired or disabled since it was cached is 401.
- **Request.** The `anthropic-version` and `anthropic-beta` rules of `/v1/messages`, and its grammar for `model`, `messages`, `system`, `tools`, `tool_choice`, `thinking` and `output_config`. Generation controls (`max_tokens`, `stream`, `temperature`, `top_p`, `top_k`, `stop_sequences`, `metadata`, `context_management`) and every other field are refused with 400 naming the field. The route's own field rules then apply as for generation: for example, images are refused on translated routes and structured output on local routes. The 2 MiB body cap applies (413, Anthropic-shaped).
- **Which count.** The route is the first deployment that routing would choose for an inference request. There is no failover, and the count is not an attempt: it updates no routing health. So a model with both Anthropic and other deployments can answer `provider` for one count and `estimate` for the next, as routing picks; the `x-omg-token-count` header labels each. When every route of the model is cooling down, the count returns 503, as generation does. On a native Anthropic route the gateway sends the validated request without `max_tokens` and `stream` to Anthropic's `/v1/messages/count_tokens`, with the connection's own credential (the client's key is never forwarded) and the client's beta values under the usual denylist. Only `input_tokens` is read from the reply (at most 16 KiB). Every other route returns the gateway estimate and calls no provider.
- **The estimate** is the UTF-8 byte length of the system text, message text, tool-call ids, names and arguments, tool results, and each tool's name, description and serialized JSON schema, divided by four and rounded up. It is an approximation, not the model's tokenizer, and can differ from the provider's count in either direction: code and non-Latin scripts usually take more tokens per byte. Thinking history is not counted, because translated routes remove it. Native Messages image blocks reach only Anthropic routes, whose own counter counts them; on every other route a Messages request with an image is refused before counting, as for generation. The estimate counts text only, and the gateway never estimates a request with an image (a guard: this release's Messages parser produces no other image a count could carry).
- **Response.** `{"input_tokens":N}`, with `x-omg-token-count: provider` or `x-omg-token-count: estimate; method=utf8-bytes-div-4`. Errors are Anthropic-shaped, as on `/v1/messages`.
- **Accounting.** A count writes no execution, reservation, hold or ledger entry and is never billed. Its result is never used as an admission bound; a later generation request is admitted on its own price limits as before. Counts do not appear in Logs or usage.
- **Rate.** A count consults no budget or rate limit and does not consume the key's request-rate allowance: that allowance is the per-minute counters that reservation and execution rows maintain, and a count writes neither. So a key that cannot run inference (over budget, rate-limited) can still count, within the count's own bounds. Those bounds exist because on Anthropic routes a count reaches the provider with the installation's credential. All are per gateway replica; the three below are configured at startup (`docs/operations.md`):
  - `GATEWAY_COUNT_TOKENS_PER_KEY_PER_MINUTE` (default 60): counts per key per UTC minute, provider-backed or estimated.
  - `GATEWAY_COUNT_TOKENS_PER_CONNECTION_PER_MINUTE` (default 600): provider-backed counts per provider connection credential per UTC minute, across all keys and workspaces, so that many keys cannot drive the installation's credential into the provider's count rate limit. Estimates call no provider and do not use this window.
  - `GATEWAY_COUNT_TOKENS_CONCURRENCY` (default 8): counts running at once, from a pool separate from generation's `GATEWAY_MAX_CONCURRENT_REQUESTS`, so a slow count never holds a generation permit. One key may have at most 2 counts running at once (fixed), so one key's counts waiting on a slow provider cannot hold the whole pool; a pool of 2 or fewer is itself the tighter bound.

  Beyond any of them the count gets 429 `rate_limit_error` before any upstream call. A count refused for concurrency (the pool or the key's two) does not spend the key's minute, so a client retrying through a full pool keeps its window; a count refused after that (an unknown model, 404, or no Messages route, 501) does spend it. `gateway_token_counts_total{outcome}` counts the counts that reached the engine by outcome (`provider`, `estimate`, `limited`, `error`), with no key, workspace or model label.
- **Cancellation and logging.** The upstream request runs inside the client's request; a disconnect cancels it, and there is nothing to settle. No prompt content, reply or credential is logged; the access log records only the route template, status and latency.

## Embeddings

Non-streaming, nonempty string or string batch; optional `encoding_format:"float"|"base64"` and positive profile-supported `dimensions`. HTTP omission or null uses float arrays. Base64 responses contain standard padded base64 of little-endian float32 vectors. The OpenAI Node SDK's ordinary `embeddings.create({model,input})` requests base64 on the wire and decodes it to numeric arrays; explicit base64 keeps strings. This does not imply universal SDK option compatibility. Token-ID arrays, unknown encodings, stream and unknown fields are rejected.

Client encoding is applied to validated normalized vectors, independently of the provider profile. Upstreams still receive float requests (Ollama receives its native non-truncating request, without an encoding field). Both upstream and client responses retain the 4 MiB cap; an interactive local formatting/size failure fails the attempt before success settlement and preserves observed usage and unresolved holds. Batch embedding lines remain float-only and explicitly refuse base64 rather than dropping it.

```json
{"model":"company/embeddings","input":["First document","Second document"],"encoding_format":"float"}
```

Limits: 128 inputs, 1 MiB aggregate string bytes, maximum 16384 dimensions, overall 2 MiB inbound HTTP and 4 MiB response. Vectors must be finite, nonempty, uniform and match input count/requested dimensions. OpenAI-wire indices must be complete and unique. Client usage is numeric protocol shape when observed, omitted when unknown; financial token values remain strings/null.

Embeddings use input-only budget/valuation and semantic output zero, not chat accounting. Ollama sends native `truncate:false` to the same approved origin/prefix; it never falls back to truncating/compatible embedding endpoints. Operators must verify server non-truncation and hard aggregate ceilings.

## Rerank

Non-streaming Cohere v2 / Jina-style subset, inference keys only, with the same workspace catalog, key restriction and routing rules as Chat:

```json
{"model":"company/rerank","query":"cat","documents":["kitten","airplane","dog"],"top_n":2}
```

The response is `{"object":"list","id","model","results":[{"index","relevance_score"}],"usage":{...}}`. `id` is the gateway request ID. Results keep provider order and are validated to have unique, in-range indices, finite scores, and a count between 1 and `min(top_n, documents)`. Documents are never echoed. `usage` contains only observed counters (`total_tokens`, `search_units`) and never fake zeros. Unknown fields, including `return_documents`, `provider` and object documents, are rejected with 400.

Limits: at most 1000 non-blank documents, 64 KiB per document, 32 KiB per query, and 1 MiB of aggregate content. `top_n` is at least 1. The body cap is `GATEWAY_MAX_BODY_BYTES_RERANK` (default 2 MiB, over the cap returns 413). Rerank is input-only: tokens are uncached input with semantic output 0. Meters are `search_units` when the provider reports them (otherwise unknown, never zero) and `requests: 1`.

Local profiles ([details](provider-adapters.md#local-rerank-and-system-one)): `openai_compatible` and `vllm` speak the same Jina/Cohere wire (vLLM on its canonical `/rerank`). SGLang returns a bare scored array; the gateway sends it no `top_n`, then sorts and truncates itself so every pair's input tokens are observed. Ollama has no rerank API.

## System One

`POST /v1/systemone` implements the TypeSafe System One contract, so the TypeSafe SDK works unchanged with `base_url = https://<gateway>`. Use an inference key.

```json
{"model":"company/clef","state":"hello there","questions":{"is_q":{"type":"noul","instructions":"Is the text a greeting?"}}}
```

- **`state`:** a nonblank string, an object, or a nonempty array. Image parts (`{"type":"image_url"}` array items) are rejected as `unsupported_capability` because no profile declares image input.
- **Questions:** 1–64 keys, each 1–128 bytes. Each question is `noul` (optional `criteria:{true,false}`), `choice` (2–255 options), or `score` (2–10 levels). `instructions` and criteria values may be strings or JSON.
- **Rejected:** client `provider`, `user` and other unknown fields. Validation failures return **422** (TypeSafe-compatible).
- **Response:** `{"id","model","answers","usage":{"input_tokens","output_tokens"}}` with TypeSafe numeric answer shapes. Choice answers carry `probabilities` and `confidence`; score answers carry `legend`, `probabilities` and `confidence`.
- **Answer validation:** answers are checked against the questions: one per key with a matching type, a choice within the options, probability keys equal to the options or levels, values finite and within [0, 1], and sums within rounding tolerance.
- **Billing:** gateway billing stays in the financial APIs and is never added to this body.
- **Admission:** input tokens are metered; output tokens are reserved up to the pinned price's `output_token_limit` (some models report free output tokens), and `requests` is 1. The body cap is `GATEWAY_MAX_BODY_BYTES_SYSTEMONE` (default 2 MiB).
- **Adapters:** OpenRouter, `openai_compatible` (TypeSafe-compatible servers such as OpenJev) and `ollama` (v0.35.0+, whose `prompt_eval_cached_count` is recorded as cache reads). vLLM and SGLang serve no System One route.

`POST /v1/images/generations`, an OpenAI-compatible non-streaming subset. Use an inference key.

```json
{"model":"company/image","prompt":"a red dot","n":1,"size":"1024x1024","quality":"low","response_format":"b64_json"}
```

| Adapter | Upstream | `size` | `quality` | `seed` |
| --- | --- | --- | --- | --- |
| `openai` | `POST /v1/images/generations`, `gpt-image-*` models only | `auto`, `1024x1024`, `1536x1024`, `1024x1536` | `auto/low/medium/high` | Unsupported |
| `openrouter` | `POST /images` | Tier `512`, `768`, `1K`, `1.5K`, `2K`, `4K` (sent as `resolution`; omitted means `1K`) | Passed through | Passed through |
| Others | No | | | |

- **Request:** `model` and a nonblank `prompt` (at most 32,000 characters) are required. `n` is 1–4 (default 1). `response_format` may only be `b64_json`. `"url"` returns 400 `unsupported_capability`, because the gateway never hosts files. Unknown fields (`output_format`, `background`, `style`, `user`, `provider`, ...) and unknown sizes/qualities are rejected with 400 `invalid_request_error`. A size, quality or seed that no deployment's adapter supports returns 400 `unsupported_capability` before admission.
- **Response:** `{"created","data":[{"b64_json","revised_prompt"?}],"usage"?}`. `usage` has only observed `input_tokens`, `output_tokens` and `total_tokens`, never fake zeros. It is omitted when the provider reports nothing.
- **Validation:** every image must be strict padded base64 whose bytes start with PNG, JPEG or WebP magic. A declared `media_type`/`output_format` must match the bytes. Exactly `n` images must be returned. URL items, SVG, unknown content fields and count mismatches fail as `invalid_upstream_response`. The attempt keeps its hold, and the provider's usage and returned-image count are recorded as evidence.
- **Limits:** the inbound body cap is `GATEWAY_MAX_BODY_BYTES_IMAGES` (default 2 MiB). The upstream response cap is `GATEWAY_MAX_RESPONSE_BYTES_IMAGES` (default 20 MiB, 1–64 MiB). It applies only to images; Messages has a 16 MiB cap; other workloads keep their 4 MiB provider cap.
- **Metering:** `output_images` is the count returned, `requests` is 1, and character/audio/search meters are semantic zeros. `output_image_variant` is the price tier: OpenAI's generated pixel size (for example `1024x1024`), or the OpenRouter tier in endpoint-pricing spelling (`768`, `1k`, `1.5k`, `2k`, `4k`). Token meters follow each provider (see [provider adapters](provider-adapters.md)).
- **Admission:** the hold is `n` × the highest priced `output_images` variant, plus input tokens at the price's `input_token_limit` and output tokens at its `output_token_limit` (image tokens cannot be bounded by the request). Character/audio/search ceilings are 0. A possible meter without a price (for example no `output_images` line) is unbounded: budgeted admission is denied with `budget_exceeded`. At settlement, a billed variant without a matching or default line is unresolved.
- Prompts and image bytes are never logged or stored.

## Audio transcriptions

`POST /v1/audio/transcriptions`, an OpenAI-compatible `multipart/form-data` subset. Use an inference key (Bearer).

```sh
curl https://gateway/v1/audio/transcriptions -H "Authorization: Bearer $KEY" \
  -F model=company/whisper -F file=@clip.wav -F response_format=json
```

- **Fields:** exactly one `file` part with a filename, `model`, optional `language` (2–3 lowercase letters), `prompt` (at most 4096 bytes), `response_format` (`json` default, or `text`) and `temperature` (0–1). `stream=false` is accepted. `verbose_json`/`srt`/`vtt`/`diarized_json`, `timestamp_granularities[]`, `include[]`, `chunking_strategy`, known-speaker fields and `stream=true` return 400 `unsupported_capability`. Any other field, a duplicate field, a filename on a text field, or a text field over 4096 bytes is 400 `invalid_request_error`.
- **Multipart parsing is strict:** a `multipart/form-data` boundary is required. There is no preamble and no epilogue beyond a final CRLF. Part headers may be only `Content-Disposition: form-data` (`name`, `filename`/`filename*`) and `Content-Type`, at most 8 KiB, and there are at most 16 parts.
- **File:** the extension of the last path component must be `flac`, `mp3`, `mp4`, `mpeg`, `mpga`, `m4a`, `ogg`, `wav` or `webm`. A part `Content-Type` must be a matching audio type, or `application/octet-stream`/absent (the extension decides). The container magic must match. The client filename is never forwarded, logged or echoed; upstreams receive `audio.<ext>`.
- **Limits:** `GATEWAY_AUDIO_MAX_UPLOAD_BYTES` caps the file part (default 25 MiB, 1 KiB–64 MiB) and returns 413. It is separate from the body cap `GATEWAY_MAX_BODY_BYTES_AUDIO_TRANSCRIPTIONS` (default 26 MiB, covering multipart framing; also 413) and from the 2 MiB JSON cap.
- **Response:** `json` is `{"text","usage"?}`, where `usage` is OpenAI's discriminated shape from observed counters only: `{"type":"tokens","input_tokens","output_tokens","total_tokens"}` or `{"type":"duration","seconds"}`. It is omitted when nothing was observed. `text` is `text/plain; charset=utf-8`. Upstreams are always asked for JSON, so usage is captured either way. Transcripts are never logged or stored.
- **Duration (server side):** the gateway measures the upload from container headers without decoding:
  - **WAV:** PCM/float/A-law/µ-law with a consistent `fmt `. Every byte after `data` counts as audio.
  - **MP3:** every MPEG frame header is walked, with ID3v2/ID3v1/APE tags skipped. Junk between frames makes the duration unknown.
  - **Ogg Vorbis/Opus:** pages are CRC-checked, there must be a single stream ending exactly at EOF, and the duration is the highest granule (Opus minus pre-skip).
  - **FLAC:** the STREAMINFO total samples. This is a declared value: an understated header makes the provider-reported duration exceed the admission ceiling, so the response is withheld (`invalid_upstream_response`) and the observed duration is still recorded against the retained hold.
  - **MP4/M4A and WebM:** not measured.
- **Metering:** `input_audio_seconds_ms` is the provider-billed duration when reported (OpenAI `usage.type:"duration"` whole seconds; OpenRouter `usage.seconds` as exact decimal text, rounded up to ms). For token-billed models (OpenAI `usage.type:"tokens"`) the tokens are recorded, and so is the measured duration when known. Unreported counters stay unknown. `requests` is 1; character/output-audio/image/search meters are semantic zeros.
- **Admission:** with a measured duration, the `input_audio_seconds_ms` ceiling is the duration rounded up to whole seconds, plus one second. A provider observation above it fails as `invalid_upstream_response`, and the usage is still recorded. Without a measurement, only the price's `max_units` bounds the meter. Otherwise the hold is unbounded and budgeted admission is denied (`budget_exceeded`). A measured ceiling above the price's `max_units` is also unbounded rather than under-held. Output tokens are reserved to the price's `output_token_limit`.
- **Pricing:** per-second/minute/hour models use an `input_audio_seconds_ms` line. Token meters a provider never charges should be `not_applicable`; unreported tokens are then semantic zeros, so the attempt can settle. For meters a model reports but does not bill (OpenRouter Whisper may report tokens; OpenAI token models also record measured audio), use explicit `"0"` lines rather than `not_applicable`.

## Speech

`POST /v1/audio/speech` (JSON) returns binary audio. Use an inference key.

```json
{"model":"company/voice","input":"Hello there","voice":"alloy","response_format":"mp3"}
```

- **Request:** `model`, nonblank `input`, `voice` (1–64 of `[A-Za-z0-9._:-]`), optional `response_format` (`mp3` default, `wav`, `opus`, `pcm`) and `speed` (0.25–4). `aac`/`flac`, `instructions` and `stream_format:"sse"` return 400 `unsupported_capability`. Other unknown fields are 400 `invalid_request_error`. A format the deployment's adapter does not produce (OpenRouter: only `mp3`/`pcm`) returns 400 `unsupported_capability` before admission.
- **Characters:** `input` is limited to `GATEWAY_AUDIO_SPEECH_MAX_INPUT_CHARS` (default 4096, at most 100,000), counted exactly as **Unicode scalar values** (Rust `char`s, not bytes or UTF-16 units) before admission. The same count is the `input_characters` meter. Providers may count differently: OpenRouter's "character" unit is not yet verified for non-ASCII text.
- **Response:** 200 with an explicit gateway `Content-Type` (`audio/mpeg`, `audio/wav`, `audio/opus`, `audio/pcm`) after the upstream media type was checked against the requested format. The body is streamed through as it arrives, without buffering. The first chunk is awaited before headers are sent, so an empty or immediately failing upstream body is a JSON error and eligible for explicit failover. Later failures, a deadline, or more than `GATEWAY_AUDIO_SPEECH_MAX_OUTPUT_BYTES` (default 64 MiB) abort the transfer. The client sees a truncated body, never a clean end. The attempt is settled only after upstream EOF and before the body completes.
- **Cancellation:** dropping the client connection drops the upstream request synchronously. The attempt is recorded as cancelled with its character usage, and the hold is retained (state unknown), because the provider may still charge.
- **Metering:** `input_characters` (exact), `requests` 1, semantic zeros for images/input audio/search. Output audio duration is never reported, so it is unknown: price `output_audio_seconds_ms` as `not_applicable`, or give it `max_units`, or the hold is unbounded. Upstreams return no usage on this route: OpenAI `tts-1`/`gpt-4o-mini-tts` token usage (only on SSE) and OpenRouter cost (only via the delayed generation lookup) are not observed, so token meters stay unknown unless priced `not_applicable`. Value per-character models such as `tts-1` ($15/M) or `microsoft/mai-voice-2-flash` ($15/M) with an `input_characters` line.
- Speech input and generated audio are never logged or stored.

## Realtime audio

`GET /v1/realtime?model=…` upgrades to a WebSocket that proxies OpenAI Realtime (GA) events. Authenticate with one inference key, either `Authorization: Bearer` or the subprotocol `openai-insecure-api-key.<key>` (never both). The key is never forwarded; the upstream uses the connection's server credential. The beta interface, ephemeral client secrets (`/v1/realtime/client_secrets`) and WebRTC/SIP (`/v1/realtime/calls`) return 400 `unsupported_capability`.

- **Client events:** an allowlist of `session.update`, `input_audio_buffer.*`, `output_audio_buffer.clear`, `conversation.item.*`, `response.create` and `response.cancel`, with field-level rules. Anything else gets an `error` event and close 1008, never a silent drop. Input transcription, automatic VAD responses, idle-timeout responses, out-of-band responses, MCP tools and image input are refused.
- **Responses:** one at a time. `response.create` always carries `max_output_tokens` (at most the window). It is forwarded only after a budget window is reserved.
- **Accounting:** one attempt and reservation per session. Usage is settled per `response.done` with the realtime audio-token meters (`input_audio_tokens`, `cache_read_audio_tokens`, `output_audio_tokens`) beside the text token meters. Unknown usage keeps its window on hold.
- **Limits:** `GATEWAY_REALTIME_*` (session length, idle time, output window, message size and event rate).
- **Termination:** a client disconnect closes upstream immediately. Only a client close frame with no response in flight ends the session as `succeeded`/`stop`. A connection lost without a close frame, or a client the gateway can no longer write to, is `cancelled`. A text frame or close reason that is not UTF-8 (close 1007) or another WebSocket protocol violation (close 1002) is `failed` (`invalid_request_error`), with any in-flight hold kept. Upstream failures close with 1011, never a clean end.

Details, limits and pricing: [realtime](realtime.md).

## Async jobs (video and batch)

Model protocols `videos` and `batches` (a legacy native-only Batch model type), each its own workload; batches of ordinary chat and embeddings models need no special protocol. Jobs belong to the creating workspace: ids are gateway ids (`video_…`, `batch_…`, `file-…`), never upstream ids, and another workspace's key gets 404. Lists come from gateway records, not the provider account.

- **Video has no supported provider.** OpenAI shut down the Sora 2 models and the Videos API on 2026-09-24, with no replacement ([OpenAI video generation guide](https://developers.openai.com/api/docs/guides/video-generation)). `POST /v1/videos` validates the request and then returns **400 `unsupported_capability`** before admission: no job, execution or hold is created. Reads of jobs created before the shutdown still work from gateway records. An OpenRouter video adapter is planned. The contract below is what that adapter will serve.
- **`POST /v1/videos`** (multipart like the SDKs, or JSON): `model, prompt` (≤ 32 KiB), `seconds` `4|8|12` (default 4) and `size` `720x1280|1280x720|1024x1792|1792x1024` (default `720x1280`), always sent upstream. `input_reference`, remix, edits, extensions and characters are `unsupported_capability`. `GET /v1/videos[/{id}]`, `GET /v1/videos/{id}/content?variant=video|thumbnail|spritesheet` (completed only; streamed, allowlisted media types), `DELETE /v1/videos/{id}` (finished jobs only).
- **`/v1/files`** is the gateway-owned [Files API](files-api.md) on the encrypted file store: `POST` (multipart `file`, `purpose`, optional `expires_after`; any field order), `GET` list (`purpose`, `limit`, `after`, `order`), `GET /{id}`, `GET /{id}/content`, `DELETE /{id}`. `batch` files are batch inputs; `user_data`, `vision`, `assistants` and `evals` are stored for phase 2 (`file_id` in requests is not implemented yet); `batch_output` files are written by the batch engine. Workspace-scoped gateway ids, storage quota (`413 storage_quota_exceeded`), never an upstream file id.
- **`POST /v1/batches`** `{input_file_id, endpoint, completion_window:"24h", metadata?}` with `endpoint` `/v1/chat/completions`, `/v1/responses`, `/v1/embeddings` or `/v1/messages`; every line is validated against that endpoint's interactive contract up front (400 `invalid_batch_input` with line numbers). `GET /v1/batches[/{id}]`, `POST /v1/batches/{id}/cancel`. `output_expires_after` is unsupported and `metadata` is not echoed. Native (provider batch API, batch price list when published) or gateway-run (one attempt and reservation per line, standard prices); see [batches](batches.md).
- **Accounting:** video jobs and native batches are one attempt and reservation each; gateway-run batch lines are their own attempts, transferred out of the batch's ceiling. Video holds `seconds × highest resolution rate`; a batch holds the sum of its lines' bounds and one "Jobs at once" slot. Unknown usage, cancellation and expiry keep holds.

## Streaming and evidence boundaries

Native upstream SSE parsers tolerate fragmented network/UTF-8 boundaries and require explicit terminal events, not EOF. Bodies are limited to 4 MiB (Messages: 16 MiB), frames to 1 MiB. Redirects, environment proxies and hidden provider retries are disabled.

Chat frontend streams incrementally. Responses streams text incrementally: `response.created`/`response.in_progress` are sent when the upstream stream opens, and each validated text delta is forwarded as `response.output_text.delta` in the message item at output index 0. Tool calls are buffered and emitted whole after the message item, so parallel calls never interleave; `response.completed`/`response.incomplete` carries the observed usage (omitted when unknown). Translated Messages streams the same way: text deltas are forwarded as `text_delta` as they arrive (in content block 0 unless reasoning precedes them; translated reasoning streams as unsigned `thinking` blocks, a new block at each switch between reasoning and text) and tool calls are emitted whole as `tool_use` blocks after them. Native Anthropic Messages instead preserves upstream content-block order and lifecycles, including thinking/signature deltas and redacted thinking. In both cases `message_delta`/`message_stop` follow engine Done. Responses keeps its 4 MiB output bound; Messages uses 16 MiB. Outside native Anthropic Messages, text is consolidated before tools because the shared text/tool view does not preserve mixed positions. Parallel tools are serialized into valid lifecycles. Engine Done alone authorizes success; malformed arguments, errors, EOF and overflow close with sanitized errors rather than success. When an upstream body or terminal snapshot fails structural validation but carries a valid usage object, the attempt still fails and keeps its hold. The validated counts are recorded on the failed execution instead of being lost. This applies to non-stream OpenAI Chat/compatible, Responses and Anthropic Messages bodies, and to the Responses stream terminal snapshot.

Dropping streams/futures requests cancellation without promising zero charges. No failover occurs after stream return.

Logs telemetry is never returned to clients: the provider-reported served model and reasoning/thinking token breakdowns are recorded per attempt only (see [provider adapters](provider-adapters.md#logs-telemetry-served-model-and-reasoning-tokens)). Client responses keep the public model alias, and invalid or absent telemetry never fails a request. See [routing](routing.md) and [provider adapters](provider-adapters.md).

The earlier “native protocol milestone 3” is historical. Isolated provider tests (including the earlier 77-test result) are not whole-stack, new-native-follow-up, real-server or production-readiness evidence. [Verification](verification.md) records dated checks separately.
