# Open Model Gateway: unreleased

Notes for changes on `main` after [v0.19.0](v0.19.0.md). They become the next release's notes.

## Gateway behavior

- The job poller now claims each video, native batch and 0016 batch with an owner, a renewable 60 s lease and a claim epoch on the job row, as the batch runner does for gateway-run batches (#651). Two gateway processes no longer poll the same job at once, and a poller that lost a native batch to another (it stalled past its lease) before it recorded the batch's results writes nothing more to it: it records no status or counts, does not finish or settle it, and deletes the result files it wrote, so a batch no longer gets duplicate, unlinked result files. A poller whose lease lapses after it recorded the results still settles the batch (settlement applies once) and deletes the provider's copies. A submission that fails after its poller lost the claim now ends `submission_interrupted` with its hold kept as unknown, where it could take the free release before. Video and 0016 batch observations are claimed but not fenced: only their state change is compare-and-set, so a stale observation can still rewrite progress, counts and display status with older values. A crashed process's jobs are polled again after about a minute. [Poller](../async-jobs.md#poller)
- **Claude Code on OpenAI-style models: reasoning and structured output** (#70, delivery 3). Messages requests to OpenAI and OpenRouter models now map `output_config.effort`, `thinking`, `output_config.format` and tool `strict` to the provider's own controls instead of dropping or refusing them. OpenAI Chat receives `reasoning_effort` and a strict `json_schema` `response_format`; it has no thinking control, so `thinking` is still dropped there. OpenRouter receives its `reasoning` object, the same `response_format` and `provider.require_parameters:true`, so it routes only to providers that support the sent parameters. Reasoning text returned by OpenRouter and by local reasoning parsers (vLLM, SGLang, Ollama) now reaches Messages clients as `thinking` blocks without a signature, in JSON and SSE, when the request enables thinking without `display:"omitted"`. Chat Completions and Responses clients still never receive it. Claude Code may replay those unsigned blocks: translated routes remove them as before, and a native Anthropic route refuses them with 400 `thinking`, also when the replayed `signature` is empty or blank (before, `"signature":""` was forwarded and refused by Anthropic after admission). When an OpenAI or OpenRouter model declines a structured-output request with a `refusal`, a Messages client now gets `stop_reason: "refusal"` and no content instead of a 502; the refusal text is not returned. Chat Completions and Responses clients still get 502 for a refusal. Local profiles keep dropping reasoning controls and refusing `output_config.format`/`strict`. Bedrock and native Anthropic are unchanged. Reasoning tokens remain inside the reported output count; holds, settlement and missing-usage handling are unchanged. No migration, runtime grant or route changes. [Claude Code field rules](../protocol-matrix.md#claude-code-field-rules)
- **Structured output and strict tools on native Anthropic and Bedrock** (#70). Messages requests to native Anthropic models now forward `output_config.format` and tool `strict` exactly instead of refusing them with 400; both are generally available on the Anthropic API and no beta header is added. Bedrock Converse now receives `output_config.format` as `outputConfig.textFormat` (JSON schema) and `strict:true` tools as `toolSpec.strict`, for Messages, Chat Completions and Responses clients; Bedrock decides per model whether it supports them and returns a validation error (HTTP 400) when it does not. Chat Completions and Responses requests with `strict:true` tools on Bedrock were refused before (HTTP 501 `unsupported_capability`); they are now sent. Reasoning content returned by Bedrock models that reason by default no longer fails the request as an invalid upstream response: it is decoded, counted in the output bound and withheld (thinking cannot be requested on Bedrock, which still refuses `thinking` with 400). Local profiles still refuse `output_config.format` and `strict` with 400; Chat Completions and Responses strict tools on native Anthropic are still refused. No migration, runtime grant or route changes. [Structured output rules](../protocol-matrix.md#structured-output-and-strict-tools-on-anthropic-and-bedrock-routes)
- **OpenRouter strict tools from every client protocol set `require_parameters`** (#70). A Chat Completions or Responses request with a `strict:true` tool on an OpenRouter model now also sends `provider.require_parameters:true`, as Messages requests already did, so OpenRouter routes it only to providers that honour every sent parameter instead of one that may ignore `strict`. What changes for existing Chat clients: such a request can no longer be served by a provider that lacks strict support; if no provider of the model supports every sent parameter, OpenRouter refuses it and the client receives HTTP 400 (`upstream_rejected`) instead of an unconstrained reply. Requests without a strict tool are unchanged.

- **A request that fails before anything was sent no longer holds budget** (#812). An admitted attempt that fails on the gateway's side before any request to the provider was built (a credential reference that cannot be resolved, an endpoint that is not approved, a request the adapter cannot encode, a Bedrock connection whose SDK finds no credentials) settles as a known zero on any price: the reservation is `settled` at 0 µUSD with zero tokens, its ledger gets the `settlement` entry, and nothing stays held or needs an administrator. Before, it stayed `unknown` with its full hold. The gateway proves "nothing sent" structurally: every provider request is built through one client type that marks the attempt when it builds a request; the error's class plays no part, so the same class after a request was built (an upstream 401) still keeps its hold. Such a failure may also fail over under a routing policy with `max_attempts>1` without `allow_ambiguous_failover`. Gateway-run batch lines follow the same rule. No migration, grant or API change. See [governance](../governance.md#settlement-and-holds) and [routing](../routing.md#failover-and-residency).

- **The database enforces the reservation lifecycle** (#641). Migration 0088 adds a row trigger on `governance_reservations` (on every partition, present and future) that refuses a state change other than `pending` → `settled`/`unknown` and `unknown` → `settled`, any change to a settled reservation's state, hold, amount, usage, price or markers, clearing an unbounded-cost marker, and a hold decrease outside settlement (a realtime session's per-response settlement and a gateway-run batch envelope's transfer into a line stay allowed; an attempt that ends unknown keeps its hold). Every writer already checked this in code and still does, first; the trigger makes a writer that lacks the check fail with SQLSTATE `23514` (`reservation_state_transition`, `reservation_settled_change` or `reservation_hold_change`) instead of changing a balance. No API or behaviour change for valid writes. [Governance](../governance.md#settlement-and-holds)

## Pricing drafts

OpenRouter operator price previews apply their structural limits only to the catalog fields the mapper reads, so speech models with long voice lists and endpoints with many unread fields are priced instead of returned as all-unknown drafts; endpoint lists of up to 256 endpoints are compared (#741). Read fields keep their limits and an over-limit endpoint response is not cached. An endpoint with comparable rates and an unreadable status is reported when it is left out of the cheapest choice, the endpoint warnings state the input and output rates that were compared, and the warning that names the endpoint a draft was priced from is never omitted. Endpoint rates in warnings are worded in the workload's units (tokens, input characters, or units where the unit is model-specific), and a catalog fallback caused by unreadable endpoint statuses says so. Provider labels are reduced to printable ASCII and fall back to the endpoint tag; a label that filtering changed, or that two endpoints share, names the endpoint's position. Each endpoint's read fields have their own value budget, and the endpoints document is projected from the response bytes without building a value tree. The catalog fetch runs one upstream request at a time, within each preview's 5-second deadline (time spent waiting included); previews waiting on a fetch that fails share its failure, and the cache holds at most 16 MiB. [Price suggestions](../governance-api.md#openrouter-price-suggestion)

## Upgrade

The poller claim (#651) needs no migration or grant change: it uses the `runner_id`, `runner_lease_until` and `runner_epoch` columns and grants of 0021 and 0081. The claim protects a job only once every gateway process runs this release. A process of an earlier release still polls with the old 30 s soft claim and ignores the lease, so drain older replicas rather than running them beside this one.

**Migration 0088** (#641) adds one trigger function and one row trigger; no grant change, no new column, no table rewrite or scan. Creating the trigger takes `SHARE ROW EXCLUSIVE` on `governance_reservations` and on each of its partitions until the migration commits: reservation writes (admission, settlement, lease reconciliation, batch admission) wait, reads do not. The catalog work took about 6 ms with 14 partitions on a test database. Each of those locks first waits for the open transactions that wrote that table or partition, and new writers queue behind the locks already taken, so the migration sets `lock_timeout` to 10 s per lock: it applies, or fails, rolls back and can be run again. Draining is not needed for correctness: v0.19.0 makes the same reservation writes as this release, none of which the trigger refuses, so its replicas keep working beside it, but drain or pick a quiet moment to avoid a write stall of up to 10 s. Cost on the hot path: the trigger function runs once per settled row (about 5 µs measured in isolation, against a settlement of about 10 ms); admission inserts and lease extensions do not run it. A load test at 40 requests/s through one gateway showed no difference beyond run-to-run noise.

## Development bootstrap

`bootstrap-dev` (and `bootstrap-demo`, which shares the check) now refuses any installation already in use: a row in any table either seed writes (accounts, grants, group mappings, cost centers, workspaces, service accounts, keys, catalog entries, budgets, audit events), execution history, or a configuration topic that has moved since migration (#743). A configuration-only database is no longer seeded with a platform admin. A repeat run on an installation with its own bootstrap marker is unchanged. The local demo's database check (for `bootstrap-demo` and for `serve` with the demo issuer) now also refuses a Unix socket (`?host=/...`), as `bootstrap-dev` already did. The refusal for a non-literal loopback host (for example `localhost`) now says to write `127.0.0.1` or `[::1]` in `DATABASE_URL`. A concurrent first OIDC sign-in is serialized with the seed by the catalog and installation locks both already take; tests now cover both orders. State only in other tables, and a loopback forwarder to a freshly migrated remote database, still pass the guard. [Local demo](../local-demo.md)

## Internal

- **Provider-specific admission and scheduling behaviour is now declared by the adapters** (#624). Whether Messages `cache_control` hints are priced at admission and in batch-line planning follows `ProviderAdapter::forwards_cache_controls` (only Anthropic), and whether a route's batch scheduling may set a priority hint follows the local profile's `accepts_priority_hint` (`vllm`, `openai_compatible`), instead of provider-name comparisons in `governance` and `jobs`. The provider-switch source check now covers `governance`, `routing` and `jobs/` with no exceptions, pins the files outside that scope that name a provider, and pins the shared submodules the scope may use. No behaviour change: the same requests admit with the same holds and prices, and the same routes accept priority hints. A new adapter that forwards cache hints sets `ProviderAdapter::forwards_cache_controls`; a new local profile whose servers accept the `priority` field sets `local::Profile::accepts_priority_hint`. An adapter that is not a local profile cannot declare priority hints today (`capabilities::accepts_priority_hint` answers `false` for it).
