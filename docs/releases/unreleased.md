# Open Model Gateway: unreleased

Notes for changes on `main` after [v0.19.0](v0.19.0.md). They become the next release's notes.

## Gateway behavior

- **A route's video options** (#52, part 1a). A Platform Admin sets the clip lengths a route accepts (the first is the default) and the sizes it accepts with the route's PATCH (`video`: `{seconds, sizes}`, or `null`), validated by the gateway (an invalid value is **400 `video_options_invalid`**, a body of another shape 422) and by the database, audited as `deployment.video_options_changed`, and returned by the route list and detail. A route without them will serve no video request. Nothing serves video yet: the inference path that reads these options lands in part 1b, and until then `/v1/videos` behaves as before. There is no Admin UI for the options yet. [Management API](../management-api.md)
- **Video generation on servers of the OpenAI video contract** (#52, part 1b). `/v1/videos` now runs on any server of the OpenAI video contract behind an approved `openai_compatible` connection (OpenAI's own Videos API shut down on 2026-09-24), on routes with video options (part 1a). Requests are matched against the caller's own routes (enabled, offered to its workspace and allowed to its key): a length or size none of them takes is refused before admission (**400 `unsupported_video_parameter`**, with `param`), and so is any field other than `model`, `prompt`, `seconds` and `size`, named in `param` (`input_reference`, `quality`, `seed`, ...); a model with no video route answers `unsupported_capability`. The options are read again under the catalog lock at admission. A video route must price video seconds (pricing v3) for every size the request may produce, as settlement values it; only such routes are chosen, and when none of the routes that take the request is priced it is refused (**400 `video_price_missing`**, budgeted or not). The length is always sent upstream, `size` only when the request names one. Settlement uses the server's reported duration (`usage.output_video_seconds` when present, and then only that, an unusable value being an unknown duration; else `seconds`) at the named size, or, when none was named, at the reported size only if the job's admitted price names it or has one rate for every size; any other reported size, an unreadable one or an unknown duration keeps the hold (cost unknown), whatever the rates; a shorter clip is billed as reported. One upstream video belongs to one job: an id the server already gave another job of the same upstream account (provider, endpoint and credential reference) is not recorded, the create answers `502`, and every job holding that id is marked `upstream_id_reused` and never asked about again (holds kept). A JSON body naming a field twice is refused, and content is passed on only from a complete `200`. Content is streamed from the server (`video/mp4`, `video/webm` or `video/quicktime` as labeled, anything else as `application/octet-stream`, with `X-Content-Type-Options: nosniff`); storing finished videos in the gateway is the next part. `DELETE` reports `upstream_deleted: false` when the server offers no delete (`405`) or the gateway cannot ask it (a create of unknown outcome, or a reused id); a `404` counts as gone. A deleted video is `404` to `GET` too. A video route counts as serving only with video options and a price admission accepts; a video model with none reads Not serving, with the reason (`video_routes_not_set_up`). Mock-tested end to end; no live video call has been made.
- **A request holds its tool schemas once** (#872). The tool definitions and the Messages envelopes of a request are shared by its attempts instead of copied for each, a Messages request's native tool definitions take their schemas from the canonical tools, and its `system` and tools are moved, not copied, when it is normalized. A body just under the structure budget now peaks at +12 to +37 MiB instead of +22 to +74 MiB ([request body structure](../operations.md#request-body-structure)). What is sent upstream is unchanged, byte for byte. No migration, runtime grant or route change.
- **JSON request bodies are bounded in what they parse into** (#872). Every JSON body of an inference route, every batch line and every realtime client frame is measured before it is parsed, and so is every JSON document a request holds in a string that the gateway parses (a tool call's `arguments`): one allocation-free pass estimates the structure it would build beyond its own bytes, and a body over 16 MiB of it is refused with 413 (`payload_too_large`, or `request_too_large` on `/v1/messages`) without being parsed or echoed; a batch line is refused as `line_too_large`, a realtime frame with an `invalid_request_error` event. Before, a 2 MiB body of tiny values (for example `[{"a":0},…]` or a tool schema holding `[0,0,…]`) parsed into up to 196 MiB before any validation and before admission; it now holds about 4 MiB. Real requests stay far below the budget: 2 MiB of real Claude Code history estimates at 3.5 to 4.8 MiB, and tool definitions reach it only at about 0.7 to 1.5 MiB of schemas. New metric `gateway_json_structure_refusals_total{route}`. **One key holds at most half the image input buffer** (never less than one body at the route cap), across its token counts and generations: beyond it that key gets 503 `image_input_busy` with `Retry-After: 1` while other keys are admitted, counted as `gateway_image_input_refusals_total{reason="key_share"}`. The embeddings `input` no longer buffers through a generic tree before it is read. The inference routes parse with the gateway's own JSON extractor (`serde_json` alone; statuses and messages unchanged). The image input buffer's worst case now counts six copies of a large body, not five (a body refused by its parse can hold an image six times over with the body): 388 MiB at the default 48 MiB, within the chart's limit. No migration, runtime grant or route change. [Request body structure](../operations.md#request-body-structure)
- **Messages images on every route, and Messages bodies above 2 MiB** (#24, delivery 3). A Messages `image` block with a base64 source is validated as Chat and Responses images are (the same type, size, count and dimension checks) and becomes the same canonical image. Translated routes now carry it in their own wire when the deployment allows `image_input`: OpenAI, OpenRouter and the local profiles a user turn's image as an `image_url` part, Bedrock a user turn's and a `tool_result`'s image as Converse image blocks; a `tool_result`'s image on an OpenAI-style or local route is refused with 400 naming `tool_result.content.image`, never dropped. Native Anthropic routes still forward the validated envelope and need no opt-in; its image data is now spliced in from the one canonical copy. `/v1/messages` and `/v1/messages/count_tokens` admit a body above 2 MiB for its images exactly as Chat Completions does (declared length, the image input buffer, the read deadlines, at most 2 MiB outside the images' base64: a long base64 string in a text block, a tool input or any other field is refused with 413), with every refusal in Anthropic's error shape. `count_tokens` with an image: Anthropic's own count on Anthropic routes; refused with 400 on a route that would estimate (Claude Code then uses its own estimate). A blocking guardrail refuses a Messages image as uninspectable, on native and translated routes alike. [Image input](../protocol-matrix.md#image-input)
- **Inline images on Anthropic and Bedrock routes** (#24, delivery 2). Chat Completions image parts now reach `anthropic` routes as Messages `image` blocks with a base64 source and `bedrock` routes as Converse `image` blocks of the decoded bytes, on deployments with `image_input` (unchanged). Responses is still served only by `openai`. An image the route's provider would refuse is refused before admission with 400 naming `image`: Anthropic's 10 MB of base64 per image, 100 images and 128 MB per request, Bedrock's 3.75 MB per image, 20 images and 20 MB per request (images and everything else sent), and 8000 px per side on both, checked from the image's header (PNG, GIF, WebP, JPEG) when it states the size. OpenAI's `detail` has no equivalent on these wires: `auto` is accepted and `low` or `high` is refused with 400 naming `detail`. Token counting is unchanged for clients: it serves only `/v1/messages/count_tokens`, whose parser produces no inline images in this release (native image blocks still reach only Anthropic routes and Anthropic's counter). The Anthropic encoder would carry inline images to that counter too, and the gateway never estimates a request with an image; both are guards here. Failover between OpenAI-shaped and Anthropic or Bedrock routes carries the image in each wire's own form, under the existing routing policy. Bedrock's SDK holds the decoded bytes and its own body, so an image there is held by up to four copies (`COPY_FACTOR` is now 4; the buffer's worst case still counts every byte at five). No `RUST_LOG` value now enables TRACE from the AWS SDK's crates, whose request events can carry a request body. [Image input](../protocol-matrix.md#image-input)
- **Inline image input on Chat Completions and Responses** (#24, delivery 1). Chat `image_url` parts and Responses `input_image` items on user messages may carry base64 data URLs (PNG, JPEG, WebP, GIF; the bytes must match the declared type; at most 5 MiB decoded each and 20 per request; OpenAI's `detail` is carried). They go only to routes whose adapter carries images (`openai`, `openrouter`, and the local `openai_compatible`, `vllm`, `sglang` and `ollama` profiles; Responses only to `openai`, the one adapter that serves Responses) and whose deployment has the new `image_input` flag, off by default; other routes are skipped before the route plan, and a request no route can take is refused with 501 `unsupported_capability` before admission. Enable the flag only for an upstream model that accepts images and bills them as input tokens: the hold stays the price's `input_token_limit` at its input rate and settlement uses observed usage; there is no image meter, so a model that also charges per image cannot be priced. Remote URLs, `file_id`, `input_file`, Chat `file` and `input_audio` parts are refused before routing with the field named, and batch lines refuse images. Chat text-part arrays are now accepted and joined into one text, as Responses input parts already were. **Request bodies:** these two routes accept a body above 2 MiB only when it declares its `Content-Length`, is at most `GATEWAY_MAX_BODY_BYTES_IMAGE_INPUT` (new, default 20 MiB), fits the per-replica `GATEWAY_IMAGE_INPUT_BUFFER_BYTES` (new, default 48 MiB), keeps arriving (no pause over 10 s, at least 128 KiB/s on average from the start, after a 128 KiB allowance, at most 180 s in all) and holds at most 2 MiB outside image data (measured before the body is parsed); otherwise 413, 408 `request_timeout`, or 503 `image_input_busy` with `Retry-After: 1` while the buffer is full. The key is authenticated before any body byte is read. Image bytes are never logged, stored or returned in an error. New metrics: `gateway_image_input_buffer_in_use_bytes`, `gateway_image_input_buffer_bytes` and `gateway_image_input_refusals_total{reason}` (`busy`, `too_large`, `timeout`). Management: deployments take `image_input` on create and PATCH (now `{enabled?, image_input?}`), return it, and audit a change as `deployment.image_input_changed`; the dashboard's Add route form and each route's actions set it. Anthropic, Bedrock and translated Messages routes still refuse images (next deliveries). [Image input](../protocol-matrix.md#image-input), [image input memory](../operations.md#image-input-memory)
- **Breaking: `GATEWAY_ADMISSION_MODE=global` is removed** (#853). The global admission mode, the rollback protocol kept since scoped admission (0027) that serialized every admission and settlement on the installation row and read authority rows `FOR SHARE`, is gone. **What to do:** an installation that set `GATEWAY_ADMISSION_MODE=global` must remove the setting (or set it to `scoped`) before upgrading; with `global`, or any value other than `scoped`, `serve` (and every other command that reads the gateway configuration) stops at startup, before the database is contacted, with an error naming the removal, and exit non-zero, so the old pods keep serving. **Nothing changes for anyone on the default** (unset or `scoped`, which the chart sets): a scoped request runs the same statements in the same lock order as before. The load test's `--admission-mode` flag is removed with it, and so are the two observations only the global mode produced: the `admission.catalog_locks` trace span and the `price` phase of `gateway_admission_seconds`. No migration, runtime grant or route change. [Governance](../governance.md#scoped-admission-lock-order)
- **An admission behind a stall is shed instead of queueing** (#132). An admission that waits more than 1.5 s for its scope's totals and counter rows, counting its wait for the replica's admission queue, now ends before anything is written or sent: HTTP 503 `scope_busy` with `Retry-After: 2` (OpenAI `type: server_error`, Anthropic `overloaded_error`), retried by gateway-run batch lines with their backoff (never failed over: every route of the scope locks the same rows), never spending the key's per-minute rate window. A realtime `response.create` shed this way gets an `error` event and the session stays open. Settlement and management waits are unchanged. Before, such requests waited for the stall to end, held a connection meanwhile and pushed the settlements behind them past their 3 s deadline. New label values of `gateway_admission_denials_total`: `code="scope_busy"`, `scope="scope_lock"`. A newly started replica on a direct PostgreSQL connection is slower for its connections' first executions, so its first burst of about 40 simultaneous requests on one workspace took about 1.7 s instead of 1.1 s and part of it can be shed; behind PgBouncer with warm server connections this was not seen (#859, [operations](../operations.md#bursts-shed-with-scope_busy)). [Governance](../governance.md#scoped-admission-lock-order)
- **`serve` opens its whole database pool before it is ready** (#132). All `GATEWAY_DATABASE_MAX_CONNECTIONS` connections are opened at once before the gateway listens and kept open, so a replica that joins under load does not open connections while its first requests wait for them. A pooler's cached failed server login is waited out while they open (#836, below); any other failure to open one of them stops startup, and when the database or pooler is out of connection slots (PostgreSQL's 53300, PgBouncer's `max_client_conn`, or no connection within the pool's 3 s acquire timeout) the message names `GATEWAY_DATABASE_MAX_CONNECTIONS`. The pool has no idle timeout any more (its connections stay open; they are still replaced after their 30-minute lifetime). Other commands still open connections when needed. The chart's Pooler `max_client_conn` default rises from 200 to 500: the HPA's 10 replicas and a rolling update's surge pod × 32 = 352, with room for old pods still draining. [Connection sizing](../postgresql-ha.md#connection-sizing)
- **Upgrade note: check the database connection budget before upgrading** (#132). Before, pools opened connections on demand and rarely reached their maximum; now every new replica needs its whole pool before it is ready. Check that `(replicas + rolling-update surge) × GATEWAY_DATABASE_MAX_CONNECTIONS`, plus one LISTEN session per replica, plus the migrator, backups and PostgreSQL's reserved sessions, fits PostgreSQL's `max_connections` (a direct connection) or each PgBouncer instance's `max_client_conn` (a pooler). The chart's surge is one pod (`maxSurge: 1`); old pods keep their connections while they drain (up to `terminationGracePeriodSeconds`), and a Deployment does not count terminating pods against the surge ([Kubernetes](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/#updating-a-deployment)), so with long-running requests count those too. If it does not fit, the new pods fail startup with a message naming `GATEWAY_DATABASE_MAX_CONNECTIONS` and exit non-zero, and the old pods keep serving. For example, the chart's defaults with a direct connection (`replicaCount: 3`, pool 32) do not fit PostgreSQL's default `max_connections` of 100 at all: 3 × 32 plus 3 LISTEN sessions is 99, against the 97 left after PostgreSQL's 3 reserved connections, so the third new pod cannot open its pool and the rollout stops there. Two ways out: lower `GATEWAY_DATABASE_MAX_CONNECTIONS`, or raise the limit (`max_connections`, or the pooler's `max_client_conn`). [Connection sizing](../postgresql-ha.md#connection-sizing)
- The job poller now claims each video, native batch and 0016 batch with an owner, a renewable 60 s lease and a claim epoch on the job row, as the batch runner does for gateway-run batches (#651). Two gateway processes no longer poll the same job at once, and a poller that lost a native batch to another (it stalled past its lease) before it recorded the batch's results writes nothing more to it: it records no status or counts, does not finish or settle it, and deletes the result files it wrote, so a batch no longer gets duplicate, unlinked result files. A poller whose lease lapses after it recorded the results still settles the batch (settlement applies once) and deletes the provider's copies. A submission that fails after its poller lost the claim now ends `submission_interrupted` with its hold kept as unknown, where it could take the free release before. Video and 0016 batch observations are claimed but not fenced: only their state change is compare-and-set, so a stale observation can still rewrite progress, counts and display status with older values. A crashed process's jobs are polled again after about a minute. [Poller](../async-jobs.md#poller)
- **Sign-in with an issuer on a private CA: `GATEWAY_OIDC_CA_FILE`** (#826). A PEM file of extra root certificates for the OIDC client only (discovery, the token exchange and JWKS), added to the public roots: an identity provider whose certificate chains to an internal CA can now be used; public issuers keep working with the setting set. Name and validity checks, HTTPS, the egress policy and every other client are unchanged (no provider, webhook, export, SMTP or file-store client trusts these roots). The file must hold CA certificates only (PEM `CERTIFICATE` sections with the CA flag, within their validity, at most 1 MiB): a missing, unreadable, empty or oversized file, any other PEM section, a server certificate or an expired CA stops startup naming the setting; so does the setting without OIDC configured. Read at startup only. Helm: `secrets.oidc.ca` mounts the bundle from a Secret or ConfigMap key. `GATEWAY_S3_CA_FILE` is unchanged. No migration, runtime grant or route change. [Identity](../identity.md#issuers-on-a-private-ca)
- **Token counting: `POST /v1/messages/count_tokens`** (#72). A new inference-key route counts the input tokens of a Messages request, with the same key, workspace and model authorization and the same request grammar as `/v1/messages` (generation controls such as `max_tokens` and `stream` are refused). On native Anthropic routes the gateway asks Anthropic's counting endpoint with the connection's own credential. Every other route gets a gateway estimate (UTF-8 bytes divided by four, rounded up), and the `x-omg-token-count` response header says which one the client received. A count writes no execution, reservation or ledger entry, is never billed and never bounds a later admission. It consults no budget or rate limit and does not consume the key's request-rate allowance. Instead each gateway replica bounds counts with three new settings: `GATEWAY_COUNT_TOKENS_PER_KEY_PER_MINUTE` (default 60), `GATEWAY_COUNT_TOKENS_PER_CONNECTION_PER_MINUTE` (default 600, provider-backed counts per provider connection credential) and `GATEWAY_COUNT_TOKENS_CONCURRENCY` (default 8, a pool separate from generation's, of which one key may hold at most 2), each validated at startup; beyond any of them the count gets 429, and a count refused for concurrency does not spend the key's minute. New metric `gateway_token_counts_total{outcome}` (`provider`, `estimate`, `limited`, `error`). Before this release the path returned 404. New route policy entry and OpenAPI operation; no migration or runtime grant changes. [Token counting rules](../protocol-matrix.md#token-counting-post-v1messagescount_tokens)

- **Claude Code on OpenAI-style models: reasoning and structured output** (#70, delivery 3). Messages requests to OpenAI and OpenRouter models now map `output_config.effort`, `thinking`, `output_config.format` and tool `strict` to the provider's own controls instead of dropping or refusing them. OpenAI Chat receives `reasoning_effort` and a strict `json_schema` `response_format`; it has no thinking control, so `thinking` is still dropped there. OpenRouter receives its `reasoning` object, the same `response_format` and `provider.require_parameters:true`, so it routes only to providers that support the sent parameters. Reasoning text returned by OpenRouter and by local reasoning parsers (vLLM, SGLang, Ollama) now reaches Messages clients as `thinking` blocks without a signature, in JSON and SSE, when the request enables thinking without `display:"omitted"`. Chat Completions and Responses clients still never receive it. Claude Code may replay those unsigned blocks: translated routes remove them as before, and a native Anthropic route refuses them with 400 `thinking`, also when the replayed `signature` is empty or blank (before, `"signature":""` was forwarded and refused by Anthropic after admission). When an OpenAI or OpenRouter model declines a structured-output request with a `refusal`, a Messages client now gets `stop_reason: "refusal"` and no content instead of a 502; the refusal text is not returned. Chat Completions and Responses clients still get 502 for a refusal. Local profiles keep dropping reasoning controls and refusing `output_config.format`/`strict`. Native Anthropic and Bedrock routes are covered by the next entry. Reasoning tokens remain inside the reported output count; holds, settlement and missing-usage handling are unchanged. No migration, runtime grant or route changes. [Claude Code field rules](../protocol-matrix.md#claude-code-field-rules)
- **Structured output and strict tools on native Anthropic and Bedrock** (#70). Messages requests to native Anthropic models now forward `output_config.format` and tool `strict` unchanged in content (object key order is not preserved) instead of refusing them with 400; both are generally available on the Anthropic API and no beta header is added. Bedrock Converse now receives `output_config.format` as `outputConfig.textFormat` (JSON schema) and `strict:true` tools as `toolSpec.strict`, for Chat Completions and Messages clients; Bedrock decides per model whether it supports them and returns a validation error (HTTP 400) when it does not. Chat Completions requests with `strict:true` tools on Bedrock were refused before (HTTP 501 `unsupported_capability`); they are now sent. Reasoning content returned by Bedrock models that reason by default no longer fails the request as an invalid upstream response: it is decoded, counted in the output bound and withheld (thinking cannot be requested on Bedrock, which still refuses `thinking` with 400). Local profiles still refuse `output_config.format` and `strict` with 400; Chat Completions strict tools on native Anthropic are still refused. No migration, runtime grant or route changes. [Structured output rules](../protocol-matrix.md#structured-output-and-strict-tools-on-anthropic-and-bedrock-routes)
- **OpenRouter strict tools from Chat Completions clients set `require_parameters`** (#70). A Chat Completions request with a `strict:true` tool on an OpenRouter model now also sends `provider.require_parameters:true`, as Messages requests already did, so OpenRouter routes it only to providers that honour every sent parameter instead of one that may ignore `strict`. What changes for existing Chat clients: such a request can no longer be served by a provider that lacks strict support; if no provider of the model supports every sent parameter, OpenRouter refuses it and the client receives HTTP 400 (`upstream_rejected`) instead of an unconstrained reply. Requests without a strict tool are unchanged.

- **A request that fails before anything was sent no longer holds budget** (#812). An admitted attempt that fails on the gateway's side before any request to the provider was built (a credential reference that cannot be resolved, an endpoint that is not approved, a request the adapter cannot encode, a Bedrock connection whose SDK finds no credentials) settles as a known zero on any price: the reservation is `settled` at 0 µUSD with zero tokens, its ledger gets the `settlement` entry, and nothing stays held or needs an administrator. Before, it stayed `unknown` with its full hold. The gateway proves "nothing sent" structurally: every provider request is built through one client type that marks the attempt when it builds a request; the error's class plays no part, so the same class after a request was built (an upstream 401) still keeps its hold. Such a failure may also fail over under a routing policy with `max_attempts>1` without `allow_ambiguous_failover`. Gateway-run batch lines follow the same rule. No migration, grant or API change. See [governance](../governance.md#settlement-and-holds) and [routing](../routing.md#failover-and-residency).

- **The database enforces the reservation lifecycle** (#641). Migration 0088 adds a row trigger on `governance_reservations` (on every partition, present and future) that refuses a state change other than `pending` → `settled`/`unknown` and `unknown` → `settled`, any change to a settled reservation's state, hold, amount, usage, price or markers, clearing an unbounded-cost marker, and a hold decrease outside settlement (a realtime session's per-response settlement and a gateway-run batch envelope's transfer into a line stay allowed; an attempt that ends unknown keeps its hold). Every writer already checked this in code and still does, first; the trigger makes a writer that lacks the check fail with SQLSTATE `23514` (`reservation_state_transition`, `reservation_settled_change` or `reservation_hold_change`) instead of changing a balance. No API or behaviour change for valid writes. [Governance](../governance.md#settlement-and-holds)

- **A video the provider may have accepted always has a job row and a hold** (#662). The job row is now recorded before the provider's create is called (without a provider id), in one transaction with the extension of its reservation's lease, and the id is filled in afterwards. A record that cannot be written sends nothing and settles the attempt as a known zero. A create that fails ends the row `failed` (`create_failed`, or `create_unconfirmed` when the provider may still have the video, hold kept); a create whose outcome is never recorded (the process died, or the id write failed) ends `create_interrupted` at the first refresh 10 minutes after it started, hold kept. Such a row is shown `queued` with no progress and is never polled upstream. Adapters may declare idempotent create (`ProviderAdapter::idempotent_video_create`); they then receive the key `omg-video-<job id>` and a create with an unknown outcome is resent once with it. No registered adapter creates videos today. [Async jobs](../async-jobs.md#video-without-a-provider-id)
- **An administrator can resolve a realtime session left unknown** (#804). `POST /api/v1/workspaces/{ws}/costs/{execution}/realtime-responses/{sequence}/reconcile` settles one unknown response of a finished realtime session from evidence (its six token counters and an evidence reference), valued with the session's pinned price; the session settles once its last unknown response is resolved, with one `reconciliation` ledger entry. Platform Admin only, with the same refusals as request-level reconciliation (nothing while the session is open, no zero without a price, no lowering of recorded usage, one settlement). `POST /api/v1/workspaces/{ws}/costs/{execution}/realtime-session/reconcile` settles a finished session none of whose responses is unknown (one killed while idle between responses, which lease expiry leaves unknown with every response settled), and states, from evidence, the usage of a request whose window the session holds without a response row (all zero allowed); the request page offers *Resolve with evidence* on each unknown response and *Settle session* on the session. [Governance API](../governance-api.md#realtime-response-resolution)

- **Access reviews on a schedule** (#481). A Platform Admin can now define a schedule: a campaign template (name, what to review, which Teams and Projects, days open) with a monthly, quarterly or yearly cadence and a start day (and, for quarterly and yearly, a start month), in UTC; a start day past a month's end means its last day. Each due run starts an ordinary campaign, recorded as started by the schedule and naming the admin who created the schedule. The gateway's lifecycle job starts each run once, also with several gateway processes; a run that dies before committing is run on the next tick; after downtime there is one late run for the latest period and earlier missed periods are not backfilled. While the schedule's previous campaign is open (or nothing or too much matches; or, for a day of retries, 20 campaigns are open or access changed during the snapshot), the run is skipped, recorded with its reason, and raises the new built-in `access_review_skipped` alert for Platform Admins once per skipped run; nothing is queued. The scheduler acts as the system: it keeps running when the creating admin is demoted or disabled and never uses their authority. New routes `GET/POST /api/v1/platform/access-review-schedules` and `GET/PATCH/DELETE /api/v1/platform/access-review-schedules/{id}` (Platform Admins manage, Auditors read, admin tokens denied); campaigns now return `schedule_id`. New audit actions `access_review_schedule.created`, `.changed`, `.paused`, `.resumed`, `.deleted`, `.run_skipped` and `access_review.started_by_schedule`. Admin › Access reviews has a Schedules section: each schedule's calendar, next start (UTC), last run with a skip's reason and the last review it started; Platform Admins create, change, pause, resume and delete schedules, Auditors read them, and a review's page says when a schedule started it. [Access review schedules](../management-api.md#access-reviews-90)

- **A rolling restart rarely loses a request on an idle keep-alive connection any more** (#850). On SIGTERM, `serve` closed every idle HTTP/1.1 keep-alive connection at once, and no earlier response had told the client to stop reusing it, so a request sent on it at that moment was lost (Node's `UND_ERR_SOCKET`; about 1 in 14,000 requests in the multi-replica rehearsal). After the first SIGTERM or Ctrl-C the gateway now keeps serving for `GATEWAY_SHUTDOWN_DRAIN_SECONDS` (new, default 5, 0 to 30) and marks every HTTP/1.1 response `Connection: close` (not a `101` upgrade, not HTTP/2 or HTTP/1.0). Then it shuts down as before: idle connections close, in-flight requests and streams finish, HTTP/2 gets GOAWAY. A second signal ends the window; 0 restores the old behaviour. Shutdown takes up to the window longer, also under Docker or Compose, whose default stop timeout is 10 s. Measured in the rehearsal: 0 failed of 64,940 requests. A client that keeps an idle connection for the whole window and reuses it just as it closes can still lose that request ([what remains](../kubernetes.md#pod-shutdown-and-rolling-restarts)). No migration, runtime grant or route change. [Pod shutdown](../kubernetes.md#pod-shutdown-and-rolling-restarts)

- **After a cooldown, one real request per route decides whether traffic resumes** (#49, part 1). Before, a route whose circuit breaker had opened took full traffic from every replica again the moment its cooldown passed. Now the route is half-open: the first request that can be the probe claims the route's probe slot (one per route across replicas, through its health row) and uses it alone. Every other request treats the route as cooling down: it uses another route of the model, or gets 503 `model_temporarily_unavailable` with `Retry-After` (the slot's remaining time, at most 5 s). A batch line not yet dispatched waits as it does for a cooldown; one already in flight when its route opens retries after its usual backoff, sends nothing to the open route, and can exhaust its retries. While the circuit is open or half-open only the probe decides: a complete success closes the circuit; a counted failure reopens it, for the deployment's `cooldown_seconds` doubled once per earlier opening, capped at 300 s (or `cooldown_seconds`, if longer). A stream closes the circuit at its first text, tool call or reasoning, and a later failure is an ordinary one; a speech stream decides at its end. The slot ends on its own after the request's timeout plus 3 s, so a dropped request or a killed process cannot keep a route closed. A failure while the circuit is open no longer extends it. Token counts and native job submissions record no health and never claim. A realtime session never claims either; it decides a half-open circuit only while no probe slot is held, so a route only realtime sessions use keeps a working breaker. The gateway sends no synthetic probes, for any provider. Migration 0093 adds the slot and the reopen count to `deployment_health` (runtime grants: `UPDATE` on the four new columns). An interactive or workload request's first attempt on a route that never failed costs the same statements as before; a failover attempt and each batch dispatch and send read the route's circuit through the health cache (one `SELECT` each with `GATEWAY_CONFIG_CACHE=off`). [Routing](../routing.md#recovery-one-real-request-decides)
- **A deployment's health says what its circuit is doing now** (#49, part 2). `GET /api/v1/platform/deployments/{deployment}/routing` adds to `health`: `circuit` (`closed`, `open`, `half_open`), `cooling_until`, `probe_in_progress` and `probe_until`, `reopen_count`, `observation` (`none`, `stale` after 600 s without one, `current`) and `as_of`, all computed when the view is read. The existing fields are unchanged. The probe's holder (an execution id) is not exposed. Admin's route page states the same in words: closed, cooling down until a time with the backoff the openings imply, half-open waiting for a request, a request testing it until a time, never observed, or not observed for over 10 minutes. No migration. [Routing](../routing.md#management-health)
- **An operator can drain a route or a connection** (#49, part 3). A Platform Admin drains a deployment, or a provider connection (all its deployments), with a reason and an optional end (`PUT /api/v1/platform/deployments/{deployment}/drain`, `/api/v1/platform/providers/{id}/drain`; `DELETE` ends it; Auditors read it). A drained route takes no new attempt (requests, failover, realtime sessions, token counts, native job submissions, batch lines, and never a half-open probe); requests already running finish. Unlike disabling it, the route stays listed in `/v1/models`, catalog-eligible and selectable, and a model whose routes are all drained answers 503 `model_temporarily_unavailable` (`Retry-After` only when a drain ends within the hour) instead of 404. Batch lines not yet dispatched wait for the drain; native jobs already submitted keep polling; a native batch not yet submitted waits too, and is submitted only while its full completion window and a 1-hour collection margin are still left before its poll deadline (with the defaults it can wait about 1 hour): past that it fails with the new error code `submission_expired`, nothing sent, its reservation settled at zero (if it ends before its envelope's lease expires; otherwise the hold is kept as unknown for reconciliation). An unsubmitted native batch is now polled past its poll deadline until it ends. The drain lifts on its own at its end. Admission refuses a drained route on every replica as soon as the drain is set (token counts, which are not admitted, within the 1 s health cache). Set, change and end are audited with the reason; Admin shows the drain on the route and connection pages, in words. [Routing](../routing.md#drain-taking-a-route-out-without-removing-it)

## Guardrails (#840, phase 1)

- **Guardrail policy layers and their management API.** A workspace-type default, a platform per-workspace override that replaces it, and a tighten-only workspace local layer (owners and admins of a Team or Project, and the owner of a personal workspace), with `local_only` on the platform layers (required on every platform PUT, since a PUT replaces the whole layer). Routes: `GET /platform/guardrails/detectors`, `GET/PUT /platform/workspace-types/{kind}/guardrails`, `GET/PUT/DELETE /platform/workspaces/{ws}/guardrails` and `GET/PUT /workspaces/{ws}/guardrails` ([management API](../management-api.md#guardrail-policies-840)). Every write names the layer it was built from: a PUT's required `expected` (`{rule_set_id, revision}`, or `null` for none) and the override reset's `?rule_set_id=&revision=` are compared with the stored layer inside the write transaction, and another layer is `409 guardrail_layer_changed` (#841); this API is new in this release, so no released client is affected. This release accepts only the pattern detector for secrets and custom patterns, with monitor and block on input; anything else is refused with `guardrail_detector_unavailable`, never stored and ignored.
- **Input rules are enforced.** Every generation request (Chat Completions, Responses, Messages, `/v1/messages/count_tokens`, gateway-run batch lines) and every embeddings request runs its workspace's rules on its input before routing and admission. A native batch, whose lines this release does not read, is refused at create time by an enforcing rule (`guardrail_not_supported`); gateway-run mode inspects each line. The pattern detector matches built-in secret shapes (cloud and service keys, tokens, private keys, JWTs, connection strings with a password, the gateway's own keys) and custom patterns. A blocking rule refuses with `guardrail_input_blocked` (400, `x-should-retry: false`, an `error.guardrail` object with the policy and rule ids, never the match); nothing is reserved and no provider is called. An enforcing rule refuses a request it cannot fully read (an image, including the image parts of Chat Completions and Responses messages, audio, an encoded document) with `guardrail_not_supported`, before anything is admitted or sent; the text beside an image is still read. A stored rule this release cannot run is shown `not_runnable` and fails under its own `on_error` (`guardrail_detector_failed`, 503). An inspection that cannot finish now (no scan slot within 1 s, the 250 ms custom-pattern budget spent, a policy this release cannot read) is refused with the retryable `guardrail_unavailable` (503, `Retry-After: 1`), never forwarded uninspected. Scan slots are bounded per workspace, and user-written patterns have their own pool. A key with 600 requests in a minute on one replica that wrote decision rows and were never admitted (refused by guardrails or by admission) gets `guardrail_rate_limited` (429) before any scan, counted in the new `gateway_guardrail_unscanned_total`; a request writes at most 16 decision rows. Gateway-run batch lines are exempt from that bound, and a line the step could not inspect now is tried again without spending an attempt. A platform layer's custom patterns are compiled once per replica, not once per workspace. Guardrail responses now say `enforced: true` and `inspected_workloads: ["generation","embeddings"]`; response text is still not inspected.
- **Decisions are recorded and visible.** Each decision (rule, revision, category, action, a count of distinct matches; never text) goes to `guardrail_events` and to `gateway_guardrail_decisions_total` and `gateway_guardrail_detector_seconds`. Logs list a refused request as `blocked` (it has no attempt), carry a `guardrail` summary on every request and the decisions in the detail, and take a `guardrail` filter; platform staff see a workspace's decisions this month as totals, also for a personal workspace. Archive guardrail history with `archive partition guardrails <month>`.
- **Dashboard pages.** Workspace › Settings › Guardrails shows the rules in effect, who set each and one sentence on what it inspects and where the text goes, and lets a Team or Project's owners and admins (and a personal workspace's owner) add rules and make the platform's stricter. Admin › Settings › Guardrails edits each workspace kind's default and lists the detectors; each Team and Project has a Guardrails tab for its override and this month's decision counts. Logs shows requests refused by guardrails, filters by guardrail decision and lists a request's decisions. [Dashboard](../dashboard.md#guardrails-840)

## Helm chart: the termination grace period (#850)

- **`gateway.terminationGracePeriodSeconds` defaults to 180 s** (was 150 s). A stopping pod can need 10 s (`preStop`) + 5 s (drain window) + 120 s (an inference accepted at its end) + 3 s (its settlement) + 3 s (exporters) + 22 s (lease release against a database that does not answer) = 163 s; 150 s was already short of the 158 s this needed without the window. The limit is sized for inference: a longer upload, a batch creation still reading its input or a realtime session is still cut off at it. A pod that finishes sooner exits sooner; a slow or stuck pod now gets up to 30 s more before it is killed (its resources stay counted against a quota meanwhile, and `kubectl drain` waits for it). A value you set yourself is kept: check it against the sum above.

## Pricing drafts

OpenRouter operator price previews apply their structural limits only to the catalog fields the mapper reads, so speech models with long voice lists and endpoints with many unread fields are priced instead of returned as all-unknown drafts; endpoint lists of up to 256 endpoints are compared (#741). Read fields keep their limits and an over-limit endpoint response is not cached. An endpoint with comparable rates and an unreadable status is reported when it is left out of the cheapest choice, the endpoint warnings state the input and output rates that were compared, and the warning that names the endpoint a draft was priced from is never omitted. Endpoint rates in warnings are worded in the workload's units (tokens, input characters, or units where the unit is model-specific), and a catalog fallback caused by unreadable endpoint statuses says so. Provider labels are reduced to printable ASCII and fall back to the endpoint tag; a label that filtering changed, or that two endpoints share, names the endpoint's position. Each endpoint's read fields have their own value budget, and the endpoints document is projected from the response bytes without building a value tree. The catalog fetch runs one upstream request at a time, within each preview's 5-second deadline (time spent waiting included); previews waiting on a fetch that fails share its failure, and the cache holds at most 16 MiB. ## Provider errors inside a non-stream 200

A provider error returned inside an HTTP 200 to a non-streaming request now has one classification across OpenAI chat, the local profiles, OpenAI Responses, Anthropic and OpenRouter, for chat, Messages, Responses, embeddings, images, audio, rerank and System One (#665). A clean envelope is classified like the same error inside a stream, so a recognised rate-limit or quota error (`rate_limit_error`, `rate_limit_exceeded`, `insufficient_quota`, a numeric 429) is `rate_limit_error`, as an HTTP 429 is. An unrecognised error is `upstream_unavailable`. An error next to output, or next to a usage value (top level or inside the error) that is not an integer zero, is `invalid_upstream_response`, and valid usage next to it is recorded as the failed attempt's evidence. [Non-stream 200 errors](../provider-adapters.md#a-provider-error-inside-a-non-stream-200)

**Upgrade note: failover and batch retries change.** No migration, grant or configuration change. Review routing policies and batch retry limits for these effects:

- A clean 200-wrapped rate limit or quota error now **fails over** to the next route when the model's routing policy allows more than one attempt, and gateway-run **batch lines retry** it under their retry limit, exactly as for an HTTP 429. Before, OpenAI chat, local, Responses and Anthropic failed such a request as `invalid_upstream_response` with no failover or retry (Messages clients of OpenAI chat and OpenRouter already saw `rate_limit_error`).
- An unrecognised 200 error on OpenAI chat, local, Responses and Anthropic is now `upstream_unavailable`: it counts against routing health, gateway batch lines retry it, and the engine fails over on it only with `allow_ambiguous_failover`. OpenRouter already classified it so.
- A 200 error next to output or nonzero usage is now always `invalid_upstream_response`: never failed over or retried. OpenRouter (any client) and Messages clients of OpenAI chat used to classify it by its code, which could fail over (`Busy`) after the provider had produced something.
- Routing health follows the new classes: 200 rate limits, quota errors and unrecognised errors now count against it on the adapters that used to report them as invalid responses (which do not count). Client-fault names (`invalid_request_error`, `authentication_error` and so on) still do not count.
- Settlement: a clean 200 `invalid_request_error` (or another rejection name) with no usage on a fully free price now settles as a known zero on every adapter, as an HTTP 400 does (OpenRouter and the Messages context-length case already did). Every other failure keeps its hold as unknown, as before.
- An empty 200 error member (`"error":{}`, `""` or `[]`) is no longer refused on its own by Responses, OpenAI embeddings and images, the local embeddings and OpenRouter: the body is decoded like any other answer, as chat already did (transcription and Anthropic still refuse an unknown member). Native batch embeddings lines with an `error` member, even a null one, fail.
- A complete non-stream provider JSON body that names a member twice in one object is now `invalid_upstream_response`, success or not: chat, Messages, Responses, embeddings, images, audio, rerank and System One (local included), Anthropic and OpenAI native batch result lines, Anthropic and OpenAI batch status bodies and OpenAI video status bodies. Stream frames and the 16 KiB read that refines an HTTP 400 are unchanged. A provider that duplicates JSON member names would start to fail; none of the supported ones does.

## Metrics

- `gateway_upstream_connections_opened_total{client}` counts the connections each pooled outbound client opens, with the same fixed `client` label as `gateway_upstream_connection_lost_total` (#611). It gives the `s3` and `export` clients a denominator for their loss counter and shows what each pool idle timeout costs. Both counters now export every client's series from startup at zero (`gateway_upstream_connection_lost_total` used to appear only after the first loss), and the example rules add `GatewayUpstreamConnectionLoss`, computed per replica. The idle timeouts stay fixed constants: a per-endpoint setting for local endpoints and tuned cloud values wait for what the two counters show in real deployments. [Lost connections](../operations.md#lost-connections-483)

## Job poller

- **Several provider jobs refresh at once** (#802). The poller used to refresh one job at a time and finish a whole pass before the next interval, so one long native collection (up to 31 minutes) held up every other job's submission, status refresh and cancel. It now keeps up to `GATEWAY_JOB_POLL_CONCURRENCY` refreshes in flight per process (default `4`, `1`–`32`, validated at startup), across intervals; each interval claims only the free slots, in one statement, so the due-job index is read once per interval rather than once per claim. Every job is still claimed once and fenced by owner, lease and epoch. [Poller](../async-jobs.md#poller)
- **Video and 0016 batch observations are fenced**: a poller whose claim ended writes nothing, a video read writes only while no poller holds the job, and progress and request counts never go back.
- **A native batch accepted after it ended** no longer has its provider id written to the ended row; it is counted in `gateway_batches_total{mode="native",event="late_submission"}` and logged with the provider batch id, and the example rule `GatewayBatchAcceptedAfterEnd` fires on it. [Job poller](../operations.md#job-poller)
- **Lease renewals are measured**: `gateway_job_lease_renewals_total{outcome=renewed|failed|lost}`, with the example rule `GatewayJobLeaseRenewalsFailing`.
- **Native batch metrics count a finish once**: a batch collected again after its first poller stopped between its finish and its settlement, or settled late after a lapsed lease, no longer counts its lines and final state twice. A batch collected again is settled from the provider's aggregate usage, when reported, without downloading its results again; otherwise the second download remains a documented cost. [Known limits](../batches.md#known-limits)

**Upgrade:** no migration or grant change. Each process now runs up to `GATEWAY_JOB_POLL_CONCURRENCY` provider refreshes at once: each holds a database connection while it writes and one upstream request while it waits, so size `GATEWAY_DATABASE_MAX_CONNECTIONS` with that in mind (the default 4 adds at most three concurrent poller connections over the earlier one). Provider rate limits on batch and video status reads see up to that many concurrent reads per process.
