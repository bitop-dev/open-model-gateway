# Open Model Gateway: unreleased

Notes for changes on `main` after [v0.20.0](v0.20.0.md). They become the next release's notes.

## Guardrails

- **What a rule does with content it cannot read (#841, migration 0100).** Unchanged by default: a Block rule keeps `uninspectable: deny`, so a request with an image, audio or a document that isn't plain text is still refused with `guardrail_not_supported` after its text is checked, and existing rules are not rewritten. New: `uninspectable: allow` on a rule lets such a request through unread, the text beside an image still checked and blocked on a match, recorded as `skipped` ("Not readable · let through" in the monthly totals, "Let through unread" on the request page). A native batch is still refused by a Block rule under either value: its lines are text a gateway-run batch reads. New: a rule may name the `images`, `audio_transcriptions` and `realtime` workloads, which this release never reads; a Block rule naming them refuses every request of that workload with `guardrail_not_supported` before admission (a realtime session before the WebSocket upgrade), and with `allow` they pass unread and record `skipped`; a realtime session's decisions are recorded with operation `realtime`. Rules that name only generation and embeddings, every rule written before, change nothing for these workloads. `allow` is the weaker value: a workspace's tightening may move a platform rule from `allow` to `deny`, never back (`403 guardrail_loosen_not_allowed`), and composition takes `deny`. Every decision now records its rule's own verdict (`refuses`), and the monthly totals split not readable decisions by it (`refuses`, null on other rows). The rule dialog says before saving when a Block rule would refuse every request of a workload for every workspace its layer reaches. ## Upgrade

### Migrations

**Migration 0100** (#841) replaces the 0092 CHECK on `guardrail_rules` that every tightening entry meets, found by its definition (exactly one must match, or the migration stops with a hint and applies nothing), with `guardrail_rules_tightening`: a tightening may now set `uninspectable`, only to `deny`, and that alone is enough for a tightening. It is validated in place, a scan of the small rules table; no stored row can violate it, because every row met the CHECK it replaces, which required `uninspectable` to be null on a tightening. It replaces the operation CHECK of `guardrail_events` the same way with `guardrail_events_operation`, which adds `realtime`, added **unvalidated** (`NOT VALID`) on the partitioned table and its month partitions (partitions created later carry it too): the list only grows, so every earlier row meets it, and validating would scan the decision history under the lock. It adds `guardrail_events.refuses` (`boolean`, nullable, no default: no rewrite), each decision's rule's own verdict, null on every earlier row, with the CHECK `guardrail_events_refuses` (every new row states it, and the decision the client was refused with refuses), unvalidated like the operation CHECK. **Apply `deploy/staging/runtime-grants.sql` before the new binary starts** (`grants apply`): it grants `INSERT` on `refuses`, which the new binary names in every decision insert, so without it every guardrail decision is refused, also for rules that existed before. **Drain the gateway before migrating** (scale it to 0; [upgrade procedure](../operations.md#upgrade-and-migration-procedure)): the migration is one transaction holding `ACCESS EXCLUSIVE` on `guardrail_rules` and on `guardrail_events` and its partitions until it commits, with `lock_timeout` 10 s (on a timeout it rolls back and can be rerun). A replica of the previous release must not serve once a rule or tightening uses the new values: it ignores a tightening's `uninspectable: deny`, so it lets through content the workspace refuses (it also writes decisions without a verdict, which the new CHECK refuses, so a request it would record fails with `accounting_unavailable`); it never runs the guard step on a realtime session, so it opens sessions a Block rule naming realtime refuses; and it reads a rule with `uninspectable: allow` or naming the new workloads as one that needs a later release, so such a rule fails under its `on_error` on every request it applies to (a fail-closed rule refuses them with `guardrail_detector_failed`, a fail-open one lets image and transcription requests through recorded as failed).
